## 1. 背景与目标

专家管理、任务对话、项目看板三份 MVP PRD 已经把「专家 = Profile、任务 = Session、项目 = Kanban Board」立住。1023 要解决的是：**岗位说明更好填、渠道专家能稳定在线、任务类型变丰富、对话更好用、配置开关对 B 端用户可见**。

### 1.1 本期原则

1. **增量，不重做底座。** 不另造专家 / 任务 / 项目模型；改 UI 表达与产品开关，底层仍走 Hermes。
2. **先对齐再细化。** 每个模块先写清诉求与开放问题，再对照 Hermes 写详细方案。
3. **Prompt 缓存仍不可破。** 岗位说明、技能、记忆、工具变更默认新会话生效（与专家 PRD §10.1 一致）。
4. **渠道能力是 session 的属性，不是进程环境变量。** 启动策略必须按「该专家是否开了渠道」解析，而不是看后端是不是桌面拉起的。

### 1.2 本期不做什么（除非后续明确纳入）

- 重写专家创建向导、看板状态机、目标拆解。
- 新增大核心 tool。
- 跨专家实时配置继承。
- **绑定 Memory Provider**（插件外挂记忆，§7.6 待定）。
- MCP **Catalog 一键安装、OAuth 登录、工具白名单、TLS 高级项**（§15.6；本期只做导入 / 测通 / 填 Key）。
- **企业微信自建应用回调（`wecom_callback`）**：产品 IM 只做智能机器人（`wecom`）+ 钉钉 + 飞书。
- **独立定时任务入口与 Hermes cron job 创建**：按时间触发的专家工作由事件中心 Timer 产生自主任务。

### 3.1 用户怎么理解

「人设」容易被写成聊天语气。这里填的是岗位说明书：负责什么、接到任务怎么推进、什么不能碰。顶部信息卡的名称 / 简介 / 标签只用于列表，**不会**写进 `SOUL.md`，模型也不会据此生成职责。

| 分段 | 填什么 | 不填什么 | 编辑器 placeholder |
|---|---|---|---|
| 岗位职责 | 负责什么、不负责什么、擅长领域 | 专家名和简介；某一次任务的需求 | 例：负责产线良率分析与工艺窗口建议；不负责设备采购决策 |
| 作业流程 | 默认怎么推进、何时问人、交什么 | 某个技能的剧本（技能 Tab）；某次任务步骤 | 例：1. 核对工作目录与数据 2. 分析 3. 结论先行 4. 高风险先问人 |
| 工作规范 | 红线、表达、审批、产物落在哪 | 具体机器路径；一次性项目约定（工作目录里的 `AGENTS.md`） | 空缓冲时见 §3.5 预填，不另写 placeholder |

岗位说明是「这个专家永远怎么干活」。整本 SOP 应放到技能，不要贴进作业流程。某次任务 / 某个目录的约定写工作目录的 `AGENTS.md`。

### 3.2 和 Hermes 怎么对齐

| 产品 | Hermes |
|---|---|
| 磁盘 | `<HERMES_HOME>/SOUL.md`。身份槽第一段（`load_soul_md`） |
| 空文件 / 文件不存在 | `load_soul_md` 得到空 → 会话用 `DEFAULT_AGENT_IDENTITY`（与 `DEFAULT_SOUL_MD` 同文） |
| Hermes 自动种入 | `ensure_hermes_home` 会把缺失或旧脚手架写成 `DEFAULT_SOUL_MD`。产品打开时：正文与 `DEFAULT_SOUL_MD` **逐字相同**（忽略首尾空白）→ 视为未填写，三段缓冲为空，**不要**把这段英文默认人格塞进岗位职责 |
| 注入截断 | 无单独 `context_file_max_chars` 时，下限 20000 字符，大窗口可放宽到最多 50 万。产品不按模型动态放宽，统一卡 20000，避免小上下文把中间截掉 |
| 缓存 | 系统提示词会话内稳定。改 `SOUL.md` 不刷新已打开对话。脚手架注释里「每次消息重新加载」**不要**写进产品文案 |

不把模板写进 `DEFAULT_AGENT_IDENTITY` / `DEFAULT_SOUL_MD`。不新增 `HERMES_*` 行为环境变量。

### 3.3 布局

```text
岗位说明
定义这个专家负责什么、怎么干活、必须遵守什么。保存后在新会话生效。

岗位职责 ●    作业流程     工作规范                    导入   导出   保存
──────────────────────────────────────────────────────────────────────
（当前子 Tab 的 Markdown 源码，单栏）

三段合计 128 / 20000
```

- 默认选中 **岗位职责**。
- 该段去掉首尾空白后非空 → 名称旁绿点。空则不打点、不标红。
- **导入 / 导出 / 保存** 作用于整份（三块一起），不是当前子 Tab。
- 切子 Tab 保留未保存缓冲，不弹确认。
- 离开本 Tab 或离开详情页时，若拼装结果与上次成功保存的全文不同：「放弃未保存的岗位说明？」
- 编辑器上方常驻：「岗位说明变更在新会话生效，不影响已打开的对话。」
- 页脚：拼装后字符数 / 20000。超过则保存禁用，文案「超过 20000 字符后，模型可能只看到开头和结尾，请删减」。

空态横幅（磁盘视为未填写，且 `profile.yaml` 没有 `soul_onboarded: true`）：

> 建议先填写岗位职责，再补作业流程与工作规范。点保存之前，新对话仍使用默认人格，不会根据专家名称自动生成。

CTA：**使用模板**、**导入**。点「知道了」写 `soul_onboarded: true`，横幅不再出现；缓冲里已预填的工作规范句保留。已有用户内容时不展示横幅。

### 3.4 拆段与拼装

磁盘格式（标题字面量不可改，解析靠它们）：

```markdown
# 岗位说明

## 岗位职责

（用户填写）

## 作业流程

（用户填写）

## 工作规范

（用户填写）
```

- 某段为空：**不输出该二级标题**。
- 三段都空：写入**存在但内容为空白**的 `SOUL.md`。不要删文件——删了下次 `ensure_hermes_home` 会种回默认人格，产品会把它再当成「未填写」，但中间若有会话读到种入文本会闪一下。
- `# 岗位说明` 可有可无；解析时忽略，不进任一段正文。

**拆段**（打开、导入）：

1. 统一换行，去掉首尾空白。空 → 三段都空。
2. 与 `DEFAULT_SOUL_MD` 逐字相同 → 三段都空（未填写）。
3. 只认这三句二级标题（行内前后可有空白）：`## 岗位职责`、`## 作业流程`、`## 工作规范`。
4. 标题之后、下一个上述标题之前的正文归入该缓冲（去掉首尾空行）。
5. **一个上述标题都没有**（旧专家、手写 SOUL）：去掉可选的 `# 岗位说明` 后，全文放入 **岗位职责**，另两段空。toast：「未识别出分段，已放入岗位职责，请按需拆到作业流程和工作规范。」不做自动摘要拆分。
6. 第一个标题之前还有正文：并入 **岗位职责**。
7. 其它 `##` 标题留在当前段正文里，不剥掉。

保存后再打开必须还原刚保存的三段。用户在正文里手写 `## 作业流程` 会切断分段——模板和 placeholder 里不要出现这三句标题。

**拼装**（保存、导出、脏检查、计字）：顺序固定为岗位职责 → 作业流程 → 工作规范，只输出非空段；段前带对应 `##` 标题；有任一非空段时文首加 `# 岗位说明`。三段都空则拼装结果为空字符串。

### 3.5 模板、预填、导入导出

**从零创建、磁盘视为未填写：** 打开时职责、流程缓冲为空；**工作规范缓冲**写入 §5.7 三句（未落盘）。绿点只在工作规范。用户不保存就离开并放弃 → 磁盘仍空，下次仍这样预填。

**复制专家：** 按磁盘拆段。工作规范为空也**不**塞 §5.7。

**使用模板**（只在横幅；已有内容时若产品仍提供入口，须二次确认「将覆盖当前三段」）：

```text
负责：
不负责：

---流程缓冲---
1. 先核对当前工作目录和已有资料
2. 做完先给结论，再给依据
3. 高风险操作先停下来问人

---规范缓冲---
（§5.7 原文，三句）
```

模板只填缓冲，不自动 `PUT`。

| 动作 | 行为 |
|---|---|
| 打开 | `GET /soul` → §3.4 拆进缓冲。未填写且从零创建 → 工作规范预填 §5.7 |
| 保存 | 三缓冲拼装 → `PUT`。超 20000 不发请求 |
| 导出 | 用**当前缓冲**（含未保存）拼成一个 `SOUL.md` 下载。不是 zip，不是三份 |
| 导入 | 选 **一个** `.md` / `.markdown`，UTF-8。按 §3.4 拆进缓冲，**尚未落盘**，再点保存才 `PUT`。解码失败 toast「无法读取，请使用 UTF-8」。若当前缓冲相对上次保存已脏，先确认覆盖 |

### 3.6 保存与生效

沿用专家 PRD §9.3，不新增路径：

```text
GET  /api/profiles/<name>/soul
     → { "content": "<SOUL.md 全文>" }

PUT  /api/profiles/<name>/soul
     Body: { "content": "<拼装全文>" }
     → { "ok": true, "effective": "next_session" }
```

可选：GET 附带 `sections: { duty, flow, rules }` 方便前端。权威字段仍是 `content`。PUT 若收到 `sections`，服务端按 §3.4 拼成一篇再写盘，禁止只写一段。

保存成功 toast（运行中会话数来自 `GET /api/profiles/<name>/sessions?status=running`）：

- N > 0：「已保存。修改将在**新会话**生效；该专家当前有 N 个运行中会话，仍使用旧岗位说明。」
- N = 0：「已保存。修改将在**新会话**生效。」

不提供「立即生效」。运行中会话的系统提示词不动。

### 3.7 实现清单与验收

| 项 | 做什么 | 不做什么 |
|---|---|---|
| Tab | 标签改为岗位说明；单栏三段 | 不保留左右预览、不加工具栏 |
| 拆装 | 前端（或 GET 附带 sections）按 §3.4 | 不拆三个文件、不三个端点 |
| 空 | 空白文件；打开时默认人格文本当成未填写 | 不删 `SOUL.md` |
| 预填 | 仅从零 + 未填写时，工作规范缓冲 = §5.7 | 不在创建向导落盘；复制不预填 |
| 模板 | 一套，横幅 CTA | 不按 tags 分套 |
| 截断 | 20000 禁止保存 | 不按当前模型窗口放宽 |

验收：

1. 详情 Tab 显示「岗位说明」，没有「人设」。从零创建进入：职责/流程空，工作规范缓冲是 §5.7，磁盘在保存前仍为空或仍是默认人格文本。
2. 只保存工作规范 → 磁盘有 `# 岗位说明` + `## 工作规范`，没有空的职责/流程标题。再打开三段还原。
3. 三段清空后保存 → 文件存在且为空白；**新**会话身份是默认人格，不是专家名称。
4. 旧 SOUL 没有这三个标题 → 全文进岗位职责，toast 提示拆段；保存后再打开仍是一段，除非用户自己拆。
5. 拼装超过 20000 字符时保存不可用。
6. 有运行中会话时保存：toast 含 N；该会话下一轮仍是旧文案；新开对话才是新文案。
7. 复制专家：源 SOUL 原样拆开，不混入 §5.7，除非源文件里本来就有。
8. 导入一个文件只改缓冲；不点保存则刷新后回到磁盘内容。
9. 导出得到的是当前三缓冲拼装的一个文件。

### 3.8 不做什么

- `GET/PUT .../soul/duty|flow|rules`
- 磁盘上三份 md、导入导出 zip、「只导出当前子 Tab」
- 保存只写当前子 Tab
- Markdown 工具栏、分栏预览、渲染预览
- 按领域标签多套模板；岗位职责硬必填
- 立即生效 / 丢弃当前会话的 prompt 缓存
- 把 §5.7 写进 Hermes `DEFAULT_SOUL_MD`

## 5. 工作空间与工作目录（设计与实现）

**对口：杜荣明、张宇**

> 已拍板（2026-09-21）。相对专家 MVP §8.6、任务对话 MVP §2.3 / §10.9：**语义不变**，把读写控制、界面、生命周期和适配层改动写成可实现规格。task-session §10.9.8 的 `@file` 扩根从 v1.1 **提前到本期必做**。

### 5.0 一页纸（已锁定）

| # | 决策 | 本期怎么做 |
|---|---|---|
| 1 | 工作空间 = 专家 | profile `config.yaml` `terminal.cwd`；一棵目录树，该专家所有对话共享浏览/读取 |
| 2 | 工作目录 = 一次对话 | session `cwd`；相对路径写、终端、附件落盘都锚在这里 |
| 3 | 新建对话默认工作目录 | **= 工作空间根**。`session.create(cwd=根, …)` 且 `explicit_cwd=true` |
| 4 | 隔离方式 | 用户把工作目录改到**已有子目录**。**不**自动建 `tasks/<session-id>/` |
| 5 | 写默认进工作目录 | 设对 session cwd 即可；相对路径已锚在 cwd。岗位说明提醒用相对路径、别发明 outputs/ |

| 12 | Prompt 缓存 | 切 cwd 不重建系统提示词；已注入的 `AGENTS.md` / 「Current working directory」字样本会话内不变 |

### 5.1 用户怎么理解

```text
专家
└─ 工作空间（一棵目录树，profile 级）
   ├─ SOP.md / 共享资料/ …     ← 所有对话都能看见、都能读
   ├─ 工位8/                   ← 某次对话可以把「工作目录」指到这里
   └─ …                        ← 未改过的对话，工作目录就是这棵树的根
```

| 产品词 | 绑在谁身上 | 用户一句话 | 不要说成 |
|---|---|---|---|
| 工作空间 | 专家 | 这个专家的文件地盘 | 不要说「项目」「看板工作目录」「Hermes 的 workspace 工具」 |
| 工作目录 | 一次对话 | 这次对话默认在哪个文件夹干活、产物默认丢哪 | 不要说「工作空间根的别名」；默认等于根，改过以后就不是 |
| 对话产物 | 当前工作目录 | 报告、导出、生成文件默认落这里 | 不要说「系统会丢到 outputs/」 |

对话记录、记忆、技能、配置仍在 `HERMES_HOME`，**不进**工作空间。

UI 文案统一用「工作空间 / 工作目录」。源码里 `_authoritative_workspace_root` **其实是 session cwd**，实现和文档不要跟它对齐产品词。

### 5.2 和 Hermes 怎么对齐

底座已经具备。产品层是**选对 cwd、把工作空间根告诉 UI 和 `@file`、用岗位说明管模型习惯**。

| 诉求 | Hermes 已有 | 产品 / 适配层 |
|---|---|---|
| 工作空间随专家 | 每 profile 自己的 `terminal.cwd`；创建时默认 `<HERMES_HOME>/workspace/`（`_PROFILE_DIRS` 只建空目录） | 工作空间 Tab：改路径、展示整棵树、上传。复制专家时**重置**为新 profile 的默认根，不拷源绝对路径（专家 MVP §8.6.2） |
| 工作目录随对话 | `session.create(cwd)`、`session.cwd.set`；`runtime_cwd` / terminal 按 task_id 记，互不串 | 新建对话传 cwd；对话页可改；列表展示相对工作空间的路径 |
| 写默认进工作目录 | `tools/file_tools_paths.py`：相对路径锚在该 session cwd | 设对 cwd。不要去改 `terminal.cwd` |
| 读整棵工作空间 | `read_file` / `search_files` 无 cwd 硬沙箱（`../` 仅软警告） | 侧边栏树根 = `terminal.cwd`；`@file` 扩 `allowed_root`（§5.4） |
| 不建每对话子目录 | Hermes 不会自建 `tasks/<id>/` | 本期也不建 |
| 运行时提示 | 已注入 `Current working directory: <session cwd>` | 可选再加一行 `Expert workspace root:`（§5.4.3），会话启动写一次 |

**Hermes 没有 `inputs` / `outputs` / `tmp` 目录约定。** `DEFAULT_AGENT_IDENTITY` / `SOUL.md` 不要求写到 `workspace/outputs`。产物就是工作目录里的相对路径（例如直接 `报告.md`）。若某专家自己要这三套目录，由岗位说明或用户 mkdir，不是核心行为。

Docker 里的 `/workspace` 是把**宿主机当前 cwd** 挂进去的挂载点，不是 `workspace/outputs`。Telegram 的 `/output/`、`/outputs/` 只是「文件可能只在容器里」的排错提示。

日常切工作目录用 `session.cwd.set`。不要用 `session.workspace.move`（连 busy 也能改库存盘路径），那是会话搬家，不是改当前干活目录。

### 5.3 读写规则

相对路径的锚点永远是**工作目录**。工作空间管「侧边栏从哪开始」和「用户 `@file` 允许指到哪」。

```text
工作空间根  D:\profiles\工艺专家\workspace\
工作目录    D:\profiles\工艺专家\workspace\          （默认，= 根）
         或 D:\profiles\工艺专家\workspace\工位8\    （用户改过）
```

| 操作 | 工作目录 = 根 | 工作目录 = `工位8/` |
|---|---|---|
| 写 `报告.md` | 落到工作空间根 | 落到 `工位8/报告.md` |
| 读 `SOP.md`（相对路径） | 根上的 SOP | 找 `工位8/SOP.md`；根上 SOP 要用 `../SOP.md` 或绝对路径 |
| 侧边栏 / 预览 | 整棵工作空间 | 仍是整棵；当前工作目录 ★ |
| terminal | 在根下执行 | 在 `工位8/` 下执行 |
| 用户 `@file:` | 根内文件都可引用 | 相对路径仍相对 `工位8/`；`../SOP.md` 与绝对路径只要落在工作空间内即可（本期扩 `allowed_root`） |

**「默认放在工作目录」不是「禁止写到别处」。** 本期不做硬沙箱。产物约束写进工作规范。

四层一起控，**不必改 core tool schema**：

```text
1. 锚点     工作空间根 = terminal.cwd     工作目录 = session cwd
2. 提示词   岗位说明 · 工作规范（§5.7）
3. 用户引用 @file / complete.path 的 allowed_root 扩到工作空间根
4. 不做     硬拦截写出 cwd 外；不教 workspace/outputs
```

| 效果 | 主要靠 | 提示词只是 |
|---|---|---|
| 产物默认进该对话工作目录 | session `cwd` | 提醒用相对路径、别发明 outputs/ |
| 读可以读整棵工作空间 | `read_file` 无沙箱 + 侧边栏 + `@file` 扩根 | 提醒共享文件用 `../` 或绝对路径 |

不要靠「改系统提示词让 Hermes 写到 workspace/outputs」实现这两句——核心没有这条约定，硬加会和「写在工作目录」打架。

### 5.4 `@file` / 补全 / 可选运行时提示（本期必做 + 可选）

#### 5.4.1 用户 `@file:`（相对 MVP 提前做）

今天 `prompt.submit`：`preprocess_context_references(..., cwd=session_cwd, allowed_root=session_cwd)`。工作目录为子目录时，`@file:../SOP.md` 和指向工作空间根的绝对路径都会报 *path is outside the allowed workspace*。

本期改为（对齐任务对话 PRD §10.9.8，从可选提前为必做）：

```text
cwd          = 该对话工作目录          ← 相对路径仍从这里解析
allowed_root = 该专家工作空间根        ← 只要解析结果落在这棵树内就放行
```

工作空间根取该 session 所属 profile 的 `terminal.cwd`（`_profile_configured_cwd(_profile_home(profile))`），不要用进程环境里的 `TERMINAL_CWD`（桌面/SSH/Cloud 拓扑会错）。

**cwd 已不在工作空间内时**（用户改过工作空间根，旧对话还指着旧路径）：

```text
若 工作目录 是 工作空间根 的子路径（含相等）→ allowed_root = 工作空间根
否则 → allowed_root = 工作目录，并在 UI 提示「当前工作目录不在工作空间内」
```

不要把两者乱合成「任意公共祖先」——那会把允许范围扩到专家地盘以外。

**`@file:SOP.md` 不会自动变成工作空间根上的 SOP。** 相对路径始终相对工作目录。侧边栏点选文件插入引用时，应插入**相对当前工作目录**的路径（必要时带 `../`），或插入绝对路径；不要插入一段解析后找不到的裸文件名。

#### 5.4.2 `complete.path`

| 场景 | root | 插入文本 |
|---|---|---|
| `@file` / `@folder` / 以 `@` 开头的文件补全 | **工作空间根**（与 `allowed_root` 同一套规则） | 写成相对**工作目录**的路径，保证提交后能通过 §5.4.1 |
| 非 `@` 的路径补全（终端） | 仍是 session cwd | 不变 |

工作空间根无效或不是目录时，两处都回退到 session cwd（与今天行为一致）。

#### 5.4.3 可选：会话启动加一行工作空间根

cwd 为子目录时，模型只看到 `Current working directory:`，不一定知道整棵树的根。允许在**会话启动、只写一次**的 volatile 环境块加：

```text
Expert workspace root: <terminal.cwd 的绝对路径>
```

会话内不再改（缓存）。工作空间根中途被用户改掉，本会话仍显示启动时的那一行；新对话才用新根。路径不要写进 `SOUL.md`（换机器即失效）。加不了也不阻塞：靠 `../` + 工作规范也能读。

越出工作空间的路径：本期不新做产品读沙箱；OS 权限内 agent 仍可能读到。UI **不引导**选工作空间外目录；选外面要二次确认（沿用任务对话 MVP）。

### 5.5 界面落点

专家详情「工作空间」Tab、任务对话侧边栏，与 MVP 同源组件（专家 MVP §8.6、任务对话 MVP §9）。本期补齐的是**语义展示和工作目录切换**，不重做文件树。

#### 5.5.1 专家详情 · 工作空间 Tab

- 树根 = 工作空间根。展示路径 +「更改路径」「新建文件夹」「上传文件」。选中至少一项后出现「删除」。
- 多选删除见 §5.5.4。本 Tab **不**改任何对话的工作目录。
- 从任务 Tab / 对话页跳入时可带 session，对应目录 ★。
- 「更改路径」= `PUT /api/profiles/<name>/workspace/root`：校验可创建 → `mkdir` → 写 `terminal.cwd`。二次确认文案须说明：**已有对话的工作目录不会自动跟着改**（见 §5.6.5）。

#### 5.5.4 多选删除文件和文件夹

只在专家详情 · 工作空间 Tab。任务对话侧边栏仍只浏览和预览，不加删除。

- 每一行（文件或文件夹）有复选框。有选中项时工具栏显示「删除 n」，并提供「全选当前列表」。
- 工作空间根本身不可选、不可删。
- 选中文件夹等于删掉该文件夹及其全部内容。父文件夹和它里面的项同时被选中时，按父文件夹删一次。
- 删除前二次确认，写清文件数和文件夹数。若选中范围包含某个对话的当前工作目录，确认文案说明：该对话的工作目录不会自动改到别处，之后相对路径可能落到已不存在的位置。
- 确认后硬删除，不进回收站。只删除解析后仍在工作空间根之内的路径。根外路径，以及指向根外的符号链接，拒绝并留在失败列表。
- 某一项失败不影响其余项。结束时 toast 写明成功几项、失败几项；失败项保持勾选。
- 不改 `terminal.cwd`，不改任何 session 的 `cwd`，不删对话记录。

### 5.6 生命周期

#### 5.6.1 创建专家

向导不配路径。后端创建空的 `<HERMES_HOME>/workspace/`，并预建 `workspace/消息渠道/`、`workspace/自主任务/`，写入 `terminal.cwd`。不预置 `定时任务/`、`inputs/`、`outputs/`、`tmp/`。自主任务中的 Timer 与其他事件触发源使用同一个目录约定，见 [experts_prd.md](./experts_prd.md)。

#### 5.6.2 复制专家

新专家工作空间根重置为**自己的** `<HERMES_HOME>/workspace/`，不沿用源专家的绝对路径（跨机器不可移植）。

#### 5.6.3 新建对话

```text
session.create
  cwd          = 该专家 terminal.cwd（工作空间根）
  explicit_cwd = true          ← 避免被进程/桌面 settle 成别的目录
```

**不** mkdir 对话专属文件夹。用户若在创建前下拉选了已有子目录，则 `cwd` 用该子目录，仍 `explicit_cwd=true`。目录必须已存在。

#### 5.6.4 对话中改工作目录

| 时机 | 能否切 | 依据 |
|---|---|---|
| 空闲（两轮之间） | 可以 | `session.cwd.set` → `_set_session_cwd` |
| 本轮 `running` | 不可以 | `session busy`（4009）；停轮后再切 |
| 工作空间根 | 本操作不改 | 只改这次对话的工作目录 |

切成功之后：

- 立刻变：状态栏、★、**下一轮**相对路径写 / 终端 / 附件锚点、`@file` 的解析 cwd。
- 不变：整棵工作空间仍可浏览、仍可读；本会话已缓存的 `AGENTS.md` 和启动时的「Current working directory」字样（缓存不可破）。新目录上的 `AGENTS.md` **不会**因切换自动注入——需要就开新对话。
- 目录须已存在（RPC 不 mkdir）。建议在工作空间内；外面二次确认。
- 多个对话可以指向同一子目录。

用户改为子目录：走 `session.cwd.set`，不新开对话。

#### 5.6.5 更改工作空间根

| 对象 | 行为 |
|---|---|
| 新对话 | 默认 cwd = 新根 |
| 已有对话 | **cwd 绝对路径保持不变**，不批量改写 |
| 侧边栏 | 立刻改以新根为树根 |
| cwd 已落到新树外的对话 | 列表/状态栏警示；`allowed_root` 回退为该对话 cwd（§5.4.1）；引导用户手动切到新树内子目录 |

不自动把旧 cwd 搬文件、不自动改写历史 session。

#### 5.6.6 归档 / 删除对话

不删工作目录里的文件（§12）。删专家按专家 MVP：profile 岛删除，工作空间目录随 profile 走，须在确认文案里写清。

### 5.7 岗位说明 · 工作规范默认句

从零创建且磁盘仍视为未填写时，预填进**工作规范缓冲**（§3.5），不自动落盘。用户可改可删。**不要**把某台机器的绝对路径写进去。

```text
生成文件使用相对路径，写在当前工作目录内；不要写到工作空间根下的 outputs/，也不要自行创建 inputs/、tmp/ 这类目录。
可以读取工作空间内的任意文件。当前工作目录之外的共享资料，使用 ../ 或绝对路径；需要搜索时，把 search_files 的路径指到工作空间根。
不要把共享 SOP 复制进每个对话目录。
```

保存后仍是一份 `SOUL.md`、下次会话生效（§3）。这是管模型习惯的层，**不能替代**设对 session cwd。

### 5.8 和其它模块的边界

| 对象 | 边界 |
|---|---|
| 岗位说明 | 专家级、跨对话有效；不写一次性路径 |
| `AGENTS.md` | 只从**工作目录**在会话**启动时**加载。共享约定放在工作空间根时，仅当工作目录=根才会自动进提示词；子目录对话靠岗位说明或 `read_file` |
| 记忆 `MEMORY.md` / `USER.md` | 在 `HERMES_HOME`，不是工作空间文件 |
| Kanban 项目工作目录 | board 级共享资源，**不是**专家工作空间。文案不要混用 |
| Docker `/workspace` | 挂的是宿主机**当前 cwd**。cwd 为子目录时，容器内默认看不见父目录。本期「读整棵工作空间」以 **local 后端 / Web 对话**为准，不改 Docker 挂载（避免碰环境实现） |
| IM 的 cwd | 消息渠道 session 默认在 `消息渠道/<平台>/<首次 session_id>/`；专属 cwd 适配见 [experts_prd.md](./experts_prd.md) |
| 自主任务目录 | `自主任务/<动作 ID>/runs/<执行 ID>/`；Timer 与其他触发源一致，见 [experts_prd.md](./experts_prd.md) |

| 项 | 改哪里 | 做什么 | 不做什么 |
|---|---|---|---|
| 新建对话 cwd | 产品调 `session.create` | cwd=工作空间根，`explicit_cwd=true` | 不 mkdir `tasks/<id>/`；不改 `terminal.cwd` |

验收测试（产品/E2E，对临时 `HERMES_HOME`，不要写 `~/.hermes`）：

1. 新专家 → 新对话：cwd 等于 `<HERMES_HOME>/workspace/`，相对路径 `报告.md` 落在根上。
2. 把工作目录改到已有 `工位8/`（空闲）：下一轮 `报告.md` 落在 `工位8/`；侧边栏仍能打开根上 `SOP.md`。
3. 工作目录为 `工位8/` 时，用户 `@file:../SOP.md` 能展开，不再报 allowed_root 越界。
4. 同一句 `@file:SOP.md` 仍解析为 `工位8/SOP.md`（相对工作目录），不偷偷改读根上的 SOP。
5. 本轮 running 时切 cwd 失败（4009 / UI 禁用）；停止后可切。
6. 更改工作空间根后，旧对话 cwd 不变；新对话默认用新根。
7. 系统提示词 / 岗位说明均不出现「请把文件写到 workspace/outputs」类句子。

### 6.1 三层不要混

| 产品对象 | Hermes | 用户怎么理解 |
|---|---|---|
| 定时任务（定义） | cron **job** | 这个专家到点要干的活：指令、时刻、投递、任务文件夹 |
| 一次运行 | cron **session**（`cron_{job_id}_{时间戳}`，`source=cron`） | 某天那次跑的记录；独立会话 |
| 对话任务 | 人开的 session | 多轮、可 HITL、可改工作目录 |

复制专家（`--clone`）**不拷** cron job，避免把「每天巡检」静默带到新专家。

### 6.2 和 Hermes 怎么对齐

| 诉求 | Hermes 已有 | 产品 / 适配层 |
|---|---|---|
| 存任务 | `<HERMES_HOME>/cron/jobs.json` | 专家作用域调已有 `GET/POST/PUT /api/cron/jobs` |
| 时间 | `parse_schedule`：每天/每周/间隔/一次/五段 cron | 复用 Dashboard `ScheduleBuilder`，不要让用户填五段表达式（可留「高级」） |
| 到点执行 | gateway 内 ticker | 有 job 就要拉起/保活该专家 gateway；创建时探测，没在跑就拉起并提示 |
| 工作目录 | job `workdir`（绝对路径，必须已存在） | 创建时 mkdir 任务主目录并写入 `workdir`；**每次 fire 再 mkdir 本次 `runs/<戳>/` 作为本轮 cwd**（见 §6.5） |
| 运行记录 | `GET /api/cron/jobs/{id}/runs`；另有 `HERMES_HOME/cron/output/` 审计文件 | 详情读 runs + session 消息；**不要**把 `~/.hermes/cron/output` 指给用户 |
| 投递 | `deliver=local` / `wecom` / `dingtalk` / `feishu` / Home | 仅产品内 → `local`；勾选 IM → 对应平台 Home。无 Home 则禁用 IM 选项 |
| 记忆 | 当前代码 cron `skip_memory=False`（专家 MVP §10.10 已过时） | 产品创建的 job：**构造 agent 时 skip_memory=True**（或等价地不加载 memory 工具）。不要靠提示词碰运气 |
| 超时 | 默认 10 分钟无活动中断（`HERMES_CRON_TIMEOUT`），不是文档里的 3 分钟 | 帮助文案写 10 分钟；本期不做超时旋钮 |
| 工具 | `_HERMES_CORE_TOOLS` 含 `cronjob_manage` | 专家默认关掉 `cronjob` toolset |

`last_status` 按 Hermes 字面展示：`ok` / `error` / `delivery_failed` / `blocked_config`。投递失败不要画成成功。

### 6.5 工作空间里的「定时任务」目录

**对话任务不改。** 下面只约束定时任务。

```text
<工作空间根>/
  SOP.md / 工位8/ / …
  定时任务/                          ← 专家级默认文件夹（创建专家时 mkdir，与 workspace 空目录一起）
    a1b2c3d4e5f6/                    ← 一个定时任务（job_id，改名不搬家）
      runs/
        20260921_090000/             ← 一次执行 = 本轮 cwd；有 write_file 产物就在这
          报告.md
        20260922_090000/
```

| 层 | 路径 | 谁创建 | 作用 |
|---|---|---|---|
| 专家默认文件夹 | `<工作空间>/定时任务/` | 创建专家（或首次建定时任务时补建） | 所有定时任务的地盘 |
| 任务主目录 | `.../定时任务/<job_id>/` | 创建该 job 时 mkdir，写入 job `workdir`（指向**这一层**） | 任务的家；jobs.json 里的 `workdir` **不要**每次 fire 改掉 |
| 本次运行目录 | `.../runs/<YYYYMMDD_HHMMSS>/` | **每次 fire 时** mkdir，本轮 session cwd 指这里 | 相对路径产物默认落点 |

时间戳与 cron session id 后缀对齐（`cron_{job_id}_{YYYYMMDD_HHMMSS}`），详情里「打开本次文件夹」才对得上。

**为什么 cwd 必须是本次 `runs/`，不能只用任务主目录：** 同一文件名（`报告.md`）会被下次运行覆盖，用户说的「每次执行的输出」就丢了。Hermes 的 `workdir` 是 job 级字段，ticker 也不会在产品 UI 里改它，所以要在 **fire 路径**（`_CronRunScope` / 等价适配）里：读出任务主目录 → mkdir `runs/<戳>/` → 本轮 cwd 用子目录。不要靠提示词让模型自己建日期文件夹。

CLI 用户给任意 git 仓库设 `--workdir` 时**不要**套这套 `runs/`（以免打乱别人的仓库）。只对**产品创建**的 job 启用：创建时在 job 上打产品标记（如 `product_scheduled: true`，随 `jobs.json` 一并保存），fire 路径见此标记再套 `runs/`。不要对所有 Hermes cron 一刀切。这是有具体消费者的适配，不是空钩子。

读写仍守 §5：相对路径锚在**本轮 cwd**（即本次 `runs/`）；读 SOP 用 `../` 或绝对路径，侧边栏仍是整棵工作空间。岗位说明里「写在当前工作目录」对定时任务仍然成立——当前工作目录就是这次运行目录。

**空跑：** 目录仍要建（cwd 必须存在）。没有 `write_file` 时文件夹可以是空的；详情写「无文件产物」，文本结果看运行记录。不要「没输出就不建目录」。

**删任务 / 改工作空间根：** 默认**不删**产物文件夹（与 §5.6.6 / §12 一致）。改工作空间根后，旧 job 的绝对 `workdir` 不变，列表警示「产物目录不在当前工作空间」；新 job 建在新根下的 `定时任务/`。

工作空间 Tab：能看见 `定时任务/` 树；任务主目录可标「定时任务」，`runs/` 下文件标「任务生成」。本 Tab 仍不改 session cwd，也不改 job。

### 6.6 详情里记什么（代替写记忆）

定时任务详情 = 这个任务的「档案」，不是 MEMORY.md。

| 区块 | 内容 |
|---|---|
| 定义 | 名称、指令、时间、投递、任务主目录、启用/暂停 |
| 调度 | 下次运行、上次运行、`last_status`、失败次数、调度在线与否 |
| 运行记录 | 每次一条：时间、状态、摘要（最终回复）、「打开本次文件夹」（`runs/<戳>/`）、打开 transcript |

运行记录来自 SessionDB cron runs + 本次工作目录文件。用户要回顾「上周巡检说了什么 / 文件在哪」，来这里，不要指望记忆 Tab。

实现：产品创建的 job 在构造 cron agent 时 **`skip_memory=True`**（当前上游默认是 False，必须显式关掉）。`skip_background_review` 保持 True。专家级记忆总闸（§7）无论开或关，产品定时任务都不写 MEMORY.md。

### 6.7 默认禁止对话里自建

- 任务对话 **不**暴露 `/cron`（任务对话 MVP 已藏高级斜杠，保持）。
- 新建专家：默认禁用 `cronjob` toolset（`cronjob_manage`）。工具 Tab 仍可打开，保存后**下次会话生效**，并提示「打开后专家可以自己创建/修改定时任务」。
- 产品 UI 是创建定时任务的主路径。

### 6.8 和渠道启动（§4）的咬合

builtin ticker 与 gateway 同进程，**没有**独立 cron 守护进程。

| 场景 | 行为 |
|---|---|
| 存在未暂停的定时任务 | 该专家 gateway **常驻**（即使 IM 全关） |
| 创建/恢复定时任务 | 探测 ticker；未在线则拉起，UI 提示「调度不在线则不会到点执行」 |
| 全部定时任务暂停或删除，且渠道全关 | 可以停 gateway |
| 只投产品内、不投 IM | 仍要 gateway（调度器在里面），不是「没渠道就不用 gateway」 |

§4.4「从未启用渠道就不常驻」改为：**无渠道且无未暂停定时任务**才不常驻。

### 6.9 实现清单与验收

| 项 | 做什么 | 不做什么 |
|---|---|---|
| 列表/CRUD | 复用 `/api/cron/jobs?profile=` | 不新造 job 表 |
| 任务主目录 | 创建 job 时 mkdir `定时任务/<id>/`，`workdir` 指这里 | 不把工作空间根或 gateway 启动目录当 cwd |
| 本次运行目录 | fire 时 mkdir `runs/<戳>/` 并作为本轮 cwd | 不每次改 `jobs.json` 的 `workdir`；不对任意 CLI `--workdir` 套 runs/ |
| skip_memory | 产品 job 构造 agent 时 True | 不改用户对话的记忆；不把经历写入 MEMORY.md |
| 投递 | 任务级设置 + 专家默认 | 不默认 `origin`（Web 创建没有 origin，会乱落到某个 Home） |
| cronjob 工具 | 专家默认关 | 不从核心 tool schema 删掉（工具 Tab 还能开） |
| 对话列表 | 过滤 `source=cron` | 不把每次 run 当成一条对话任务 |

验收：

1. 新专家工作空间下有空的 `定时任务/`。建一条「每天 9 点」任务后，出现 `定时任务/<id>/`。
2. 立即跑一次：出现 `runs/<戳>/`；相对路径 `报告.md` 落在该次目录，不落在工作空间根、也不覆盖另一次运行。
3. 详情能看到这次回复和文件夹；记忆 Tab / MEMORY.md **没有**被这次运行改写。
4. 投递改为 IM Home（渠道已配）后，下次成功运行会发到 Home，详情里仍有记录；改回仅产品内则不再发 IM。
5. 对话里专家没有 `cronjob` 工具（默认）；任务 Tab 仍能建定时任务。
6. 未暂停 job + 渠道全关时，gateway 仍在；停掉全部 job 后才允许停调度。
7. 对话任务列表里看不到 `cron_...` session。

### 6.10 事件任务（历史根级绑定方案，已调整）

> **2026-09-30 决策：本节原来的 `handler_type=expert` + 根级 `expert_id` 不能表示一个事件的多分支、多动作。** 本期「自主任务（事件中心）」按专家执行动作绑定；Timer 是事件中心触发源，不与其它事件类型分开。当前规则见 [experts_prd.md](./experts_prd.md) §1.2.3 与附录 B；下文保留早期设计记录。

> 已拍板（2026-09-28）：事件中心继续负责事件接入和全部事件任务。专家页增加「事件」分段，只做「这条事件触发后运行这个专家」。两边读写**同一条**事件任务，不另建表，也不做双向同步。

#### 6.10.1 三处各管什么

| | 事件中心 · 事件接入 | 事件中心 · 事件任务 | 专家 · 任务 · 事件 |
|---|---|---|---|
| 管什么 | Webhook、Kafka、MQTT、Pulsar、Timer 等事件源 | 全部绑定：工作流、插件、规则引擎、通知、专家 | 只显示 `handler_type=expert` 且 `expert_id=当前专家` 的任务 |
| 在这里做 | 建源、填地址和密钥、启停源 | 选源，再选处理方式 | 选一个已有事件源，写这个专家怎么跑 |
| 不在这里做 | 不写专家提示词、工作目录 | 不改岗位说明、工作空间、IM | 不新建事件源，不做条件分支、规则引擎、自适应引擎 |

专家页「新建」插入的就是事件中心那张任务表：`handler_type=expert`，`expert_id=当前专家`。规则引擎、自适应、钉钉通知等块不出现。保存后事件中心列表能看到同一条，处理对象是这个专家。事件中心把某条改成「运行某专家」后，该专家页出现同一条。

#### 6.10.2 和定时任务分开

专家的「定时」分段仍是 Hermes cron（§6），不读事件中心。事件中心的 Timer 如果绑的是某个专家，只出现在该专家的「事件」分段，不进「定时」。不要为同一件事配两套钟。

事件任务不是 cron job：不写入 `cron/jobs.json`，不出现在对话任务列表，不自动建看板卡。

#### 6.10.3 数据：一份记录

不建「专家事件任务」表，不做定时对账。

| 字段 | 谁写 |
|---|---|
| 事件源 id、源的地址和密钥 | 只有事件接入 |
| `handler_type`、`expert_id` | 事件任务。专家页新建时写死为当前专家 |
| 提示词模板、工作目录、投递 | 存在这条任务上。专家页编辑；事件中心打开「运行该专家」时改的也是这些字段 |
| 规则、自适应、通知动作 | 同一条上的非专家字段，只有事件中心编辑 |
| 运行记录、触发次数 | 挂在任务 id 上，两边只读 |

专家页列表查询：

```text
事件任务 where expert_id = 当前专家 and handler_type = expert
```

事件源改名后，两边刷新都读到新名字，专家侧不存源名称副本。

| 操作 | 结果 |
|---|---|
| 专家页新建 / 修改 / 启停 / 删除 | 直接插入或更新这一条。事件中心同一条一起变 |
| 事件中心把「专家」改成工作流 | 清空 `expert_id`。专家页这条消失，任务仍在事件中心 |
| 事件中心把工作流改成某专家 | 写上 `expert_id`。该专家页出现这条；提示词、工作目录、投递若空，用 §6.10.4 的默认 |
| 停用事件源 | 任务还在。两边显示「事件源已停」，不再触发。任务自己的启停不跟着被改写 |
| 删除专家 | 这些任务停用，并标「专家已删除」。不静默删任务，事件中心保留记录 |
| 复制专家 | **不**复制事件任务 |

保存带版本号或更新时间。提交时版本旧了，提示「已被别人改过，请刷新」，不覆盖。

#### 6.10.4 专家页上怎么配

任务 Tab 分段为 **对话 | 定时 | 事件**。事件段只列定义，不把每一次触发当成一条对话。

一条任务要配：

| 项 | 规则 |
|---|---|
| 事件 | 只能选已存在的事件接入。不能在这里填 Broker、生成 Webhook、改密钥 |
| 启停 | 只停「跑这个专家」，不停事件源 |
| 提示词 | 模板，可插入本次事件 payload。空则只用 payload |
| 工作目录 | 默认 `<工作空间>/事件任务/<任务 id>/runs/<本次>/`，每次触发新建，作为该次 cwd。与 `定时任务/` 分开 |
| 投递 | 与定时任务相同：仅产品内，或发到已配置的 IM Home |
| 记忆 | 与定时任务相同：这次运行不写 MEMORY.md / USER.md |

运行日志：专家页显示该任务最近几次（时间、成败、产物目录）。完整日志和统计用事件中心同一任务 id 的运行记录，不另抄一份。

#### 6.10.5 不做什么

- 专家页再做一套事件接入，或再存一份任务表再同步。
- 把事件中心 Timer 并进 Hermes cron。
- 事件触发去 resume 某条人工对话，或自动建看板卡。
- 在专家页配置规则引擎、条件分支、插件工作流。

## 7. 记忆开关（设计与实现）

> 已拍板（2026-09-21）：产品做一个**总闸**，关掉时 **`memory_enabled` 与 `user_profile_enabled` 一起关**（不拆成经验/画像两个 UI 开关）。记忆 Tab 仍只读两份文件。**Memory Provider 绑定本期不实现，见 §7.6 待定。**

不新增核心 tool。写入路径本来就是已有的 `memory` 工具；本期只把「开不开」做成专家可见的开关。

### 7.0 一页纸（已锁定）

| # | 决策 | 本期怎么做 |
|---|---|---|
| 1 | 一个总闸 | 记忆 Tab 上「启用记忆」。开 = 两项 config 都 `true`；关 = **两项都 `false`** |
| 2 | 不拆两个 UI 开关 | 卡片仍分专家经验 / 用户画像（只读），但启停不分开 |
| 3 | 关掉之后 | 新会话：不注入两份文件进系统提示词；`memory` 工具从 schema 消失（`check_fn` 两项都假则不可用） |
| 4 | 已有文件 | **不删**。Tab 仍可看，卡片标「记忆已关闭」 |
| 5 | 生效 | **仅新会话**（prompt 缓存）。toast 同岗位说明 |
| 6 | 默认 | 与 Hermes / 专家 MVP 一致：**开**（文件可以仍是空的，表示「有能力记」） |
| 7 | 自主任务 | 事件中心触发的专家执行不写 MEMORY.md，与总闸开无关；见 [experts_prd.md](./experts_prd.md) |
| 8 | Provider | **待定**（§7.6）。本期 UI 不出现绑定入口 |

### 7.1 用户怎么理解

Tab 只读不等于专家不会记。总闸开着时，对话里模型可以调 `memory` 写入；关掉后新会话不再写、也不再把旧记忆喂给模型。

```text
记忆
这个专家是否在对话里记住经验和用户画像。关闭后新会话不再写入、不再召回。

启用记忆  [开]

专家经验（MEMORY.md）     用户画像（USER.md）
（只读卡片，容量/更新时间同专家 MVP §8.8）
```

关着时两张卡片保留内容 + 角标「已关闭」；空文件仍走 MVP 空状态，并加一句「当前已关闭记忆，即使有内容也不会进入新对话」。

### 7.2 和 Hermes 怎么对齐

| 产品 | 落盘 |
|---|---|
| 总闸开 | 该专家 `config.yaml`：`memory.memory_enabled: true` 且 `memory.user_profile_enabled: true` |
| 总闸关 | 两项都写成 `false`（一次保存写齐，禁止只改其中一个） |
| 只读展示 | 仍读 `<HERMES_HOME>/memories/MEMORY.md`、`USER.md` |

关闭后 Hermes 行为（不必产品再包一层拒绝写入）：

- `check_memory_requirements` 为假 → 内置 `memory` 工具不出现。
- 系统提示词不注入 MEMORY/USER 块，也不再给记忆指导句。
- 磁盘文件原样保留。

**硬约束（即使 Provider 待定也要知道）：** 两项都假时，若将来绑了 Memory Provider，其工具和提示词块也会被同一道闸藏掉。做不到「关内置、只用外挂」。本期无 Provider UI，但总闸的语义按这个实现，避免以后打架。

工具 Tab 里的 `memory` toolset：记忆 Tab 是主开关。若有人在工具 Tab 把 `memory` 整组关掉，记忆 Tab 提示「对话里的记忆工具已关」。不要做两套静默对敲。

不走 MCP，不为记忆新造核心 tool，不新增 `HERMES_*` 行为环境变量。

### 7.3 关掉时用户说「记住：…」

新会话没有 `memory` 工具。产品不为此往系统提示词塞额外句子（避免无必要改缓存前缀）。Tab 上「已关闭」即可。不保证模型口头怎么回答；验收只要求 schema 里没有 `memory`。

### 7.4 复制 / 创建专家

- 新建：总闸默认 **开**，memories 文件仍按专家 MVP 强制空。
- 复制：文件仍清空；总闸随 `config.yaml` 走（源专家关着则新专家也关）。不要在复制时单独改记忆开关。

### 7.5 实现清单与验收

| 项 | 做什么 | 不做什么 |
|---|---|---|
| 总闸 | 一次写入两个 config 键 | 不提供只关经验、只关画像 |
| 展示 | 复用 MVP 只读两卡 | 不做记忆 CRUD（仍属专家 PRD P1） |
| 接口 | 该专家 profile 的 config 读写（带 `profile`） | 不写 default 专家的 config |
| Provider | 无 | 见 §7.6 |

验收：

1. 新专家默认总闸开；空记忆 Tab 仍是 MVP 引导，不是「已关闭」。
2. 关掉并保存 → toast 新会话生效；**新开**对话的工具列表没有 `memory`；系统提示词没有 MEMORY/USER 块。
3. 关掉后再打开 Tab：两份旧文件还在，标「已关闭」。
4. 再打开总闸 → 仅新会话恢复工具与注入。
5. 总闸开着运行自主任务：MEMORY.md 仍不被该次执行改写。
6. 记忆 Tab 没有「绑定 Provider」入口。

## 8. 技能获取渠道标签与主动习得开关

> 产品需求已定：获取渠道只有「从平台导入」「本地上传」「习得」「专家模板」四类；「主动习得」是专家级开关。与技能启用状态、技能写入审批分别展示和存储。Hermes 现有能力与产品渠道的映射、接口及迁移方案待实现时细化。

### 8.1 获取渠道标签

每个技能有且只有一个**获取渠道**。专家详情的技能列表显示渠道标签并支持按渠道筛选；现有技能详情入口如展示来源，须使用同一标签。标签文案与含义固定为：

| 标签 | 稳定值（建议） | 何时赋值 |
|---|---|---|
| 从平台导入 | `platform_import` | 通过产品的平台导入流程取得技能时 |
| 本地上传 | `local_upload` | 用户上传本地技能包或文件并创建技能时 |
| 习得 | `learned` | AI 根据对话内容创建技能时，包括主动习得和用户明确要求的学习 |
| 专家模板 | `expert_template` | 用户复制专家模板并取得其中的技能时 |

- 渠道在技能进入该专家时写入，后续编辑、更新内容或启停不改变它；从专家模板复制得到的是新技能，标「专家模板」。
- 来源信息可补充具体平台、上传文件名、模板 ID / 版本等；这些是渠道的附加信息，不增加第五个渠道。主动与用户明确要求的学习可另存触发方式，不拆成两个渠道。
- 获取渠道是产品数据，不能直接用 Hermes 当前的 `bundled` / `hub` / `agent` 来源分类代替；其中 `agent` 同时包含 Agent 创建与本地手写技能，不能一律标「习得」。已有技能须按可核实的创建记录迁移，无法判定的记录先核实来源，不凭目录或使用次数猜测。
- 技能启用/禁用仍控制是否加载使用，不改变获取渠道；来源标签也不表达更新许可。

### 8.2 主动习得开关

专家详情 · 技能 Tab 增加专家级开关 **「主动习得技能」**，默认开启，按当前专家 profile 保存。开关只管 Hermes 在普通对话中**未经用户明确要求**而主动沉淀技能的行为：

| 开关 | 对话与后台复盘中的行为 |
|---|---|
| 开 | 可主动创建新技能，也可把新的可复用经验补进现有技能 |
| 关 | 不主动创建或修改技能；已有技能仍可加载使用，记忆的自动复盘不受影响 |

用户明确要求创建或修改技能（包括执行 `/learn`）时，两种开关状态下都允许发起；若开启了现有 `skills.write_approval`，这些写入仍须审批。从平台导入、本地上传和复制专家模板也不受此开关限制。

开关与技能启用状态是两条独立的轴：关闭「主动习得技能」不批量禁用已有技能；禁用某个技能也不改变专家能否习得其他技能。设置变更默认**新会话生效**，不重建运行中会话的系统提示词或工具列表；界面保存后提示这一点。

### 8.3 与 Hermes 对齐及验收

- 仅将 `skills.creation_nudge_interval` 设为 `0` 不够：它只停定期提示，前台仍有鼓励 `skill_manage` 的指引。关闭开关时需同时处理前台引导、后台技能复盘，并在技能写入处区分自主行为与用户明确指令。不能靠模型自报的参数判断授权来源。
- `auxiliary.background_review.enabled: false` 会停掉整个后台复盘，连记忆也受影响；产品开关应只停技能习得。`skills.write_approval` 是写入审批，不是主动习得开关。
- 不新增核心工具或 `HERMES_*` 行为环境变量。配置按 profile 落盘，并遵守会话内提示词与工具集稳定的缓存约束。

验收：

1. 四种获取流程产生的技能分别显示对应标签；列表筛选与详情标签一致，编辑或启停后标签不变。
2. 关闭主动习得后，新会话的普通对话及后台复盘均不会自主新建或修改技能；已有技能仍能加载，记忆复盘仍可运行。
3. 开关关闭时，用户明确要求学习 / 修改技能仍可完成；开启写入审批时，该写入先进入待审批状态。
4. 复制专家模板得到的技能标「专家模板」；不能把 Hermes 的所有 `agent` 技能或仅被使用过的技能误标为「习得」。

### 9.2 主动沟通

默认关。打开后两张表，不是两个大文本框。

```text
主动沟通          [关]

可私聊的人                         [添加]
张三    （平台 ID，界面对用户隐藏）  移除

可发的群                           [添加]
项目群  （平台 ID，界面对用户隐藏）  移除
```

| 渠道 | 单聊存 | 群存 | 添加方式 |
|---|---|---|---|
| 飞书 | 用户 `open_id`（`ou_`） | 群 `chat_id`（`oc_`） | 群：机器人 `im +chat-list --as bot` 或 `im +chat-search --as bot`。人：从已有入站身份／已知 ID 选取；若要按姓名搜索，需另有用户授权的 `contact +search-user --as user` 或产品通讯录。机器人列会话拿不到单聊 |
| 钉钉 | 用户 `userId`；@ 时还要 `openDingTalkId` | 群 `openConversationId` | 机器人发送不认姓名、群名。先搜成唯一 ID 再写入。`send-by-bot` 的 `--users` 与 `--group` 不能同时传 |
| 企微 | 会话 `chat_id`（`chat_type=single`） | 会话 `chat_id`（`chat_type=group`） | 只从 `message aibot sessions list` 勾选。通讯录 `userid` 不能当发送 ID，手填拒绝 |

企微名单是白名单，不是发信地址。发送前重新拉最近会话，只发给「名单里有，并且本次列表里也有」的目标。授权人用 `identity whoami`，标成「始终可发」。最近会话大约只有 10 个；写进名单但最近没聊过的，发不出去。

专家说「发给张三」「发到项目群」时，只在这两张名单里匹配。重名就问，不匹配就停止。

| 动作 | CLI |
|---|---|
| 飞书单聊 / 群 | `im +messages-send --as bot --user-id` / `--chat-id` |
| 钉钉单聊 / 群 | `send-by-bot --users` / `--group` |
| 企微 | `message aibot send`，目标先过「名单 ∩ 本次最近会话」 |

开关关掉：不能按名单主动发。别人在当前对话里找专家，不受影响。

### 9.3 群里 @

只发生在「可发的群」中的某一个群，并且主动沟通开着。

- 飞书：`im +chat-members-list --as bot` 确认成员后，在文本消息里 @ 其 `open_id`。文件消息不能带 @。
- 钉钉：群消息使用 `--at-user-ids` 或 `--at-open-dingtalk-ids`。文件和 @ 分成两条。
- 企微：无平台 @。只能把消息发进名单内的群。

### 9.4 允许收发文件

与主动沟通并列，默认关。

| | 主动沟通关 | 主动沟通开 |
|---|---|---|
| 收发文件关 | 当前对话只回文本。不收文件，不发文件，不主动找人 | 可按名单发单聊、发群、在群里 @。不收发文件 |
| 收发文件开 | 当前对话可以收文件，也可以把工作目录里的文件回给对方。不能按名单发到别的人或群 | 名单内可以发文本、@、发文件。当前对话可以收文件 |

- **收（当前对话）**：对方发来的图片、文件、语音、视频落到该对话工作目录。开关关则不落地、不交给专家。三家都走适配器入站，不看名单。
- **发**：从工作目录拿文件。企微 `wecom-cli media upload --json '{"file_path":"..."}'` 取得 `media_id`，再 `message aibot send`；钉钉机器人用 `dws chat message send-by-bot --robot-code ... --msg-type file --file-path ./文件`（`--group` 与 `--users` 互斥；统一 `+messages-send --as bot` 在本机 v1.0.59 不支持 Bot 文件）；飞书 `lark-cli im +messages-send --as bot --file ./文件` 自动上传。按名单发时，主动沟通也要开着。当前会话回复可复用 Hermes 企微／飞书适配器的本地文件发送；钉钉 session webhook 适配器不支持本地文件，走 `dws` 机器人发送。
- **事后下载历史文件**：本期可优先做飞书 `im +messages-resources-download --as bot` 或列表 `--download-resources`。钉钉 `dws chat +messages-resource-download`、企微 `wecom-cli media download` 也有下载能力，但其可用身份与资源 ID 来源须另验证；历史补拉不作为当前对话实时收文件的前置步骤。平台对原生语音／视频格式有限制，必要时按普通文件附件发送。

要 @ 又要发文件：主动沟通开着发一条文本；收发文件开着再发一条文件。

### 9.6 验收

1. 三个渠道页没有群聊策略、允许用户；飞书没有域名 / 连接模式 / Encrypt Key / Verification Token。
2. 企微没有「群聊需 @」；钉钉、飞书有，默认开。
3. 主动沟通、允许收发文件默认关。关着时不能按名单发消息、不能收发文件；当前对话文本回复仍可用。
4. 飞书、钉钉添加人或群时，重名必须选择后才写入；企微只能从最近会话勾选，手填 userid 被拒绝。
5. 主动沟通开、收发文件关：名单内可发文本和 @，发文件被拒绝，当前对话收到的文件不落地。

8. 飞书文件消息不带 @；需要 @ 时另有一条文本。

### 9.7 实现方案概要（2026-09-30 源码与 CLI 核对）

1. **入站与 session**：企微、钉钉、飞书继续用 Hermes gateway 适配器接收消息；`SessionSource` → `SessionStore.get_or_create_session` 按 profile／平台／会话／用户路由。产品在取得新 session ID 后，建立 `消息渠道/<平台>/<首次 session_id>/` 并持久化、绑定该 session 的 cwd；媒体缓存或下载文件在交给 agent 前归档到此目录。仅建文件夹或改专家 `terminal.cwd` 均不足以实现每个 IM 任务独立 cwd。
2. **自主任务**：事件中心负责 Timer 等触发与专家动作绑定；每次命中动作，在专家 Profile 作用域内复用 Hermes `AIAgent` + SessionDB 创建独立 `source=event_center` session，cwd 为 `自主任务/<动作 ID>/runs/<执行 ID>/`。事件中心保存动作／执行记录与 session ID，产品不通过 Hermes cron 创建定时 job。详细链路见 [experts_prd.md 附录 B](./experts_prd.md#附录-b-新增任务的-session-与目录方案待确认)。
3. **主动发送与产品开关**：专家可以直接调用各厂商的机器人 CLI。若「主动沟通」开关和名单只是操作引导，可由技能／工作规范在调用前检查；若必须成为强制限制，产品才提供受控出站入口，持有调用凭据并在发送前校验目标、开关、名单与文件路径。允许通用终端直接使用完整凭据时，UI 开关无法构成强制限制。
4. **机器人命令与调用资格**：企微 [`message aibot send`](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-message/SKILL.md) 以 AI Bot 身份发送，CLI 扫码[授权](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-shared/SKILL.md)只用于取得调用资格；钉钉 `+messages-send --as bot` 或 [`send-by-bot --file-path`](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/multi/dingtalk-chat/references/chat/chat-bot.md) 以应用机器人发送；飞书 [`im +messages-send --as bot`](https://github.com/larksuite/cli/blob/main/skills/lark-im/references/lark-im-messages-send.md) 以应用 Bot 发送。三者都不需要以真人身份展示消息。当前版本核对与各平台限制见 [experts_prd.md 附录 D](./experts_prd.md#附录-d-实现方案概要源码与厂商-cli-核对)。

| cron 运行 session | `source=cron` | 对话列表本就过滤（§6.3），归档 UI 也碰不到 |

`hidden`、`pinned`、`ended_at` **不要**拿来当产品归档。归档 = `sessions.archived`。

### 15.1 用户怎么走（步数要少）

MCP Tab 顶部保留「添加」和「从平台导入」。从平台导入使用与技能 Tab 相同的选择弹窗，按「我导入的／我创建的」筛选并批量选择已有服务；它与 Hermes Catalog 一键安装不是同一能力。

「添加外部 MCP 服务」弹窗内分「粘贴配置／手动添加」两页：

1. **粘贴配置**：接受 mcp.json 的三种外壳格式；解析预览列出服务名与 Streamable HTTP、SSE 或 stdio。导入按名称合并，同名覆盖，JSON 未提及的服务保留。解析失败不写盘。
2. **手动添加**：连接方式提供 Streamable HTTP、SSE、本地命令 stdio 三选一。前两项填写服务地址与认证信息；stdio 填启动命令、参数和环境变量。确认按钮为「添加并测试」。
3. **从平台导入**：从平台已有服务选择；导入后保留原 transport，并对启用的服务逐台测试。缺密钥时继续使用一次填齐的密钥表。

列表使用卡片：右上角开关负责启停，卡片主体打开详情；详情区分启用状态与连接状态，展示实际发现的能力。右下角更多操作包括「测试连通」「配置操作」「删除服务」。测试与配置都进入同一详情弹窗，连接失败摘要保持可见。配置修改暂存，保存后自动测试并提示新会话生效。

测试必须调用该专家 profile 的 Hermes 探针并获取工具列表；原型中的模拟结果仅用于页面演示。已禁用服务可手动测试，批量导入时只自动测试本次导入且已启用的服务。OAuth 条目仍提示使用 CLI `hermes mcp login <名>`。

### 15.2 粘贴格式（只收 JSON）

接受下列之一（UTF-8 文本；可带 Markdown 代码围栏，导入前剥掉）：

```json
{ "mcpServers": { "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" } } } }
```

也认 `mcp_servers`（Hermes 自己的键名）以及 **没有外壳、直接 name→config** 的 map。单台服务器对象（有 `command` 或 `url` 但没有名字）**拒绝**，toast：「需要服务器名称，请包成 `{"mcpServers": {"名字": {…}}}`」。

每条必须有 `command`（stdio）或 `url`（Streamable HTTP / SSE），不能两个都无。`url` 未指定 `transport: sse` 时按 Streamable HTTP 处理；指定 `transport: sse` 时保留 SSE；`command` 按 stdio 处理。其它键按 Hermes 原样写入（`args` / `env` / `headers` / `auth` / `enabled`）。`timeout`、`tools`、`ssl_verify` 等若 JSON 里有就存，**UI 不编辑**。

名字写入 `mcp_servers` 的 key：转成小写，只留 `a-z0-9_-`；非法字符变 `-`。改名时 toast「`Foo Bar` → `foo-bar`」。重名（含改名后撞上已有）走覆盖规则。

**不解析**：裸 `npx …` 命令、`claude mcp add …`、Cursor deeplink、YAML。用户用这些时 toast：「请粘贴 mcp.json」。

### 15.3 密钥怎么落盘

原则与 Hermes 一致：`.env` 存秘密，`config.yaml` 只引用。

| JSON 里的值 | 导入时 |
|---|---|
| `${VAR}` 或 `${env:VAR}` | 原样写入 yaml；若 `.env` 无此 VAR 或为空 → 列入「填写密钥」 |
| `env` 里键名像密钥（`KEY` / `TOKEN` / `SECRET` / `PASSWORD` / `AUTH` 等，对齐 `hermes import-agent` 的启发式）且值为明文 | 写入 `.env` 该键（已有非空则 **不覆盖**，避免导入冲掉专家已配的 key），yaml 改成 `${键}` |
| HTTP `headers.Authorization` 为 `Bearer <明文>` | 写入 `.env` 的 `MCP_<服务器名>_TOKEN`（名里的 `-` 变 `_`、大写），header 改成 `Bearer ${MCP_<服务器名>_TOKEN}` |
| 已是 `Bearer ${VAR}` | 只检查 VAR 是否已有值 |

「配置」表（行内点开只含 **这一台** 用到的变量；导入后自动弹出时可跨多台一次填齐）：

- 每行：变量名 + 密码框。已有值的不回传明文，占位「已配置，留空则不改」；有输入才覆盖 `.env`。
- 一次保存，走该专家 `PUT /api/env?profile=`（或现有等价接口）。不提供「是否作为密钥」勾选——本期凡进这张表的都进 `.env`。
- 保存成功后对该服务器 **自动测连通**。

列表接口不回传明文；行状态只区分有/无密钥。

### 15.4 测连通

复用 Hermes `POST /api/mcp/servers/{name}/test?profile=`（内部 `_probe_single_server`）。真连、拉 `tools/list`，不要只看「字段填没填」。

- 导入写入后：对 **本次导入的每台** 自动测（已禁用的不测）。
- 填密钥保存后：对 **用到这些变量的服务器** 自动测。
- 行内 **测试连通**：只测这一台，启用/禁用都可点。
- `auth: oauth` 且磁盘无 token：按 API 现有语义失败，行文案用上面的 OAuth 提示，不要报成普通「连接失败」。

并发：一次导入多台可并行测，单台失败不影响其它行。超时用 Hermes 默认 `connect_timeout`，产品不加超时输入框。

测通 **不** 等于当前对话已能调 MCP 工具。toast 仍说新会话生效；有运行中会话时带 N（同 MVP §8.11.5）。

### 15.5 和 MVP / Hermes 的接口

| 动作 | 落盘 / API |
|---|---|
| 列表、启停、删除、简化添加 | 仍专家 MVP §8.11 / §9.8 |
| 导入合并 | 读现有 `mcp_servers` → 合并 → 写回。优先复用带 `profile` 的 Dashboard：`GET /api/mcp/servers` + 逐台 `POST` 或读改写；**不要**对整表 `PUT /api/mcp/servers` 做替换（那会删 JSON 里没有的服务器） |
| 测通 | `POST /api/mcp/servers/{name}/test?profile=` |
| 密钥 | 该专家 `.env`（`save_env_value` / `PUT /api/env?profile=`） |

本 Tab 仍是专家模块 UI，不跳转 Hermes Dashboard `/mcp` 页。可以复用其 API 与探针，不要重写一套 MCP 协议。

`hermes -p <专家> mcp test <名>` 必须与 UI 测同一份配置。

### 15.6 明确不做

- Hermes Catalog 一键安装、`hermes mcp install`（平台已有服务的选择导入在本期支持）
- UI 内 OAuth（`mcp login`、Dashboard 授权流）
- 工具勾选 `tools.include` / `exclude`（JSON 带来的过滤原样保留，界面不改）
- mTLS、自定义 CA、`ssl_verify`
- 整份 mcp.json 双向编辑器（只要导入，不要当配置 IDE）
- 粘贴 npx / deeplink / `import-agent`
- 导入后默认 `/reload-mcp` 或中途改系统提示词
- 新核心 tool；Memory Provider 仍不准进本 Tab（§7.6）

### 15.7 验收

1. 粘贴标准 `{"mcpServers":{…}}`（含 `${TOKEN}`）→ 导入成功 → 缺 token 则 **自动弹出一张密钥表** → 保存后行变 🟢 或给出连接失败摘要；yaml 无明文 token。
2. 粘贴带明文 `GITHUB_PERSONAL_ACCESS_TOKEN` 的 JSON → 导入后 `.env` 有值、yaml 为 `${…}` → **无需再填**，自动测。
3. 专家已有服务器 A，导入只含 B → A 还在；导入与 A 同名 → A 被覆盖并 toast。
4. 非法 JSON / 无名字的单对象 → 不写盘。
5. **每一行**都有「测试连通」「配置」（含 🟢 正常、已禁用）；测试结论与 `hermes -p <该专家> mcp test <名>` 同类。
6. 🟢 行点「配置」可改已有 token（留空不改）；保存后自动再测。无密钥变量的行点「配置」得到说明 toast，不弹空表。
7. MCP Tab 没有 Catalog、OAuth 按钮、工具白名单、TLS 表单项。
8. 保存/导入 toast：新会话生效；有运行中会话时带 N。
