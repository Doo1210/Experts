# IM 消息渠道产品需求文档

Status: design proposal  
Target: Hermes 专家（Profile）· 消息渠道

本文档讨论专家通过钉钉、飞书和企业微信消息渠道与用户沟通的产品能力。一个专家对应一个 Hermes profile，每个 profile 拥有独立的渠道配置、机器人凭据、允许名单和工作空间。

## 第一章 主动沟通实现方案

### 1.1 目标与范围

专家可以以**当前 profile 绑定的企业应用机器人身份**，向已批准的单聊对象或群聊主动发送文字、图片和文件。运行时直接调用平台接口或复用现有适配器，不调用钉钉、飞书、企微 CLI，也不依赖员工个人 OAuth 登录态。

本章的“主动沟通”是**跨消息会话的新发送**：

- 用户从桌面、网页或任务对话要求专家向某个消息渠道的人或群发送。
- 用户在消息渠道会话 A 中下指令，要求专家向另一个消息渠道会话 B 发送。A、B 可以属于同一平台，也可以跨平台。
- 已获批准的定时任务或业务规则触发向名单目标发送。

用户通过消息渠道给专家发消息，属于正常入站；专家回复**发来指令的当前会话**，属于现有回复链路。这两种行为不受“主动沟通”名单约束。仅打开主动沟通开关和添加名单，不意味着专家可以无任务或规则触发地自行广播。

MVP **不做**目标 Hermes session 的新建、镜像、主动发送后的会话历史关联或后续回复连续性。发送使用目标平台 ID；独立保存发送流水，供本次结果反馈、故障排查和后续审计使用。本期“消息渠道”页不提供独立的发送记录按钮或弹窗。

### 1.2 页面配置与能力开关

钉钉、飞书、企业微信各自配置以下状态，不能用一个总开关替代：

1. **启用渠道**：机器人接收并回复该渠道消息的基础连接状态。
2. **主动沟通**：默认关闭；开启后，专家才可向该渠道允许名单中的其他会话发起新消息。关闭时保留名单，后端立即拒绝该渠道新的主动发送。
3. **允许收发图片与文件**：默认关闭；控制当前对话中的图片、文件处理和发送。向名单目标主动发图片或文件时，主动沟通与该开关必须同时开启。普通文字主动发送只要求主动沟通开启。

Home 会话只用于默认结果投递，不自动成为主动沟通目标。“群聊需 @”只控制别人向群内专家发消息时专家是否响应，与专家主动发群分开。

三家渠道各写明机器人类型：企微为 AI Bot，钉钉为企业内部应用机器人，飞书为企业自建应用机器人。钉钉凭据使用 Client ID、Client Secret，Robot Code 与 Client ID 不同时可选填；钉钉不展示“扫码配置”，企微和飞书可保留各自入口。

页面上的“测试”会真实向目标发送消息，必须明确显示目标、发送者机器人、测试内容和结果。渠道“已连接”、目标“已加入名单”与平台“当前可发送”是不同状态，不得合并为同一个绿色标识。

### 1.3 允许名单与目标 ID

每个 profile、每个平台维护“可私聊的人”和“可发的群”。**三家的目标发现能力不同，不能设计成同一个平台候选列表**：

- **钉钉**：MVP 以输入并核对 `userId` / `openConversationId` 为主；已收到的单聊、群聊消息可提供快捷选择。具备相应通讯录权限时可查询员工 ID，但通讯录结果不证明机器人可发送；不能默认枚举机器人可发的全部群。
- **飞书**：具备群信息权限时，可按机器人身份列出或搜索机器人所在、可见的群；单聊没有对应的“机器人所有私聊对象列表”，人员来自入站消息中的 `open_id`，或具备通讯录权限时的应用身份查询。必要时可输入 ID 核对。
- **企业微信 AI Bot**：不使用 CLI 时，MVP 从该机器人在 Hermes 中已收到的消息和事件整理已互动会话；不接受任意通讯录 `userid` 直接入名单。本地历史记录不能证明平台当前仍允许发送。`wecom-cli message aibot sessions list` 是另一个 CLI 产品的能力，不能当作 AI Bot WebSocket SDK 已提供的会话枚举接口。

三家都需要管理员核对目标身份和稳定平台 ID 后明确批准。Hermes 的 `gateway/channel_directory.py` 可提供历史会话线索，但其人工别名占位及名称解析结果**不是**发送授权，也不保证当前可达。

名单记录至少包含：

- 产品生成的不透明 `target_id`，供专家工具调用；模型不接触平台原始 ID。
- 所属 profile、平台和目标类型（单聊或群聊）。
- 平台原生目标 ID、平台显示名称、批准状态及最近验证时间。
- **用途说明（选填）**：描述这个人负责什么或这个群用于什么。页面添加人员、添加群可显示不同示例，但共用一个数据字段。MVP 不单独要求用户填写“别名”。用途说明是可编辑的目标资料，不是发送授权或给专家的指令。

渠道目标 ID 的含义不同，不能统一复用 Hermes `session_id`：

- **钉钉**：单聊使用企业用户 `userId`（入站 `sender_staff_id` 可作候选）；群聊使用 `openConversationId`（入站 `conversation_id` 可作候选）。机器人必须有发送权限，群发前须确认机器人在目标群内。
- **飞书**：单聊使用当前应用可用的用户 `open_id`；群聊使用 `chat_id`。群聊入站已有 `chat_id`；适配器当前对发送者 ID 有优先级选择，产品层需可靠保留发送所需的 `open_id`。应用可用范围和群成员关系仍由平台约束。
- **企业微信 AI Bot**：单聊使用已建立机器人会话的用户标识，群聊使用群 `chatid`。只加入该机器人确曾互动且经管理员批准的会话，不凭通讯录中的任意 `userid` 给陌生人冷启动私聊。发送前检查本 profile 的连接及目标记录；在没有机器人身份会话列表接口的情况下，不能预先保证目标当前可达，须以实际发送回执或错误判断。

机器人刚加入一个群而尚未收到消息时，基于历史会话的候选可能为空；飞书可在具备权限时尝试机器人可见群接口，钉钉和企微的历史互动入口则需写明首次发现步骤，例如让群成员与机器人发生一次实际消息交互。若允许管理员手动提供平台 ID，必须核对该 ID 对应的目标与当前机器人适用范围，不能把未经核对的 ID 直接放入可发送名单。目标获批不等于发送已成功，实际可达性仍以平台发送结果为准。

**Hermes 入站来源的边界。** [`gateway/session.py`](../../gateway/session.py) 的 `SessionSource` 保存平台、会话类型、`chat_id`、发送者主/备用 ID 及可选 profile，创建 session 时来源会写入 `origin_json`；`session_id` 和 `session_key` 均不是可直接提交给平台的目标 ID。现有 session 的 origin 可能保留创建时的来源快照，后续入站不能依赖它补齐当时缺失的 ID。`gateway/channel_directory.py` 将来源压缩为 ID、名称、类型等展示字段，还允许人工别名占位；它只提供候选线索，不表示当前机器人可发送，更不是批准名单。

- 钉钉适配器将群 `conversation_id` 作为 `chat_id`；收到 `sender_staff_id` 时将其放入 `user_id_alt`，可作为单聊 `userId` 候选。单聊的 `chat_id` 可能是 `conversation_id`，不能直接当 `userId`。见 [`plugins/platforms/dingtalk/adapter.py`](../../plugins/platforms/dingtalk/adapter.py)。
- 飞书适配器保存群 `chat_id`，但发送者主 ID 优先取 `user_id`，否则才取 `open_id`；两者同时存在时，产品所需的 `open_id` 不会作为独立字段保存在 session origin。需从入站事件明确保留当前应用的 `open_id`。见 [`plugins/platforms/feishu/adapter.py`](../../plugins/platforms/feishu/adapter.py)。
- 企微 AI Bot 的单聊来源使用发送者 `userid`，群来源使用 `chatid`。近期交互可作为候选，但当前群发送路径在缺少内存中的 `req_id` 时会拒绝；session 不保证当前可达。见 [`plugins/platforms/wecom/adapter.py`](../../plugins/platforms/wecom/adapter.py)。

落地时应在**入站事件处**建立按 profile、平台和机器人身份隔离的目标线索记录，保留原生 ID 及其类型、名称、来源、最近互动时间；不能只从 `session_id`、session key 或目录展示名反推。线索与经管理员批准的 `target_id` 记录分开保存。

### 1.4 暴露给专家的统一工具

产品通过 profile 作用域的插件注册**一个** `proactive_message` 工具，放在独立工具集 `proactive_messaging` 中；不把通用跨渠道发送加入 Hermes core 工具。工具只包含两个 action：

- `list_targets`：参数可含 `kind`、`platform`、`query`，均非必填。省略 `platform` 时跨当前 profile 所有已开启主动沟通的渠道列出已批准目标；名单较短时返回完整列表。每项只含 `target_id`、平台、类型、名称、选填的用途说明和必要的状态信息。
- `send`：只接受 `target_id`、可选文字 `text`、可选工作空间相对路径 `file`；文字和文件至少提供一项。MVP 一次至多一个文件。`send` 不接受模型传来的 profile、机器人凭据、平台原始 `chat_id`。

专家的操作顺序：先用已有文件能力确认文件，再调用 `list_targets` 看允许名单，用用户指令、名称、用途说明和平台上下文判断目标；只有唯一且明确时调用 `send`。跨平台同名、多个合理候选、仅有牵强匹配或没有匹配时先询问用户，不能默认第一项或编造 ID。目标名单和用途说明应按需通过工具结果提供，而非反复改写长期会话的系统提示。

示例：用户说“把工作空间的质检报告发到质量分析群”。专家先确认唯一文件路径，再列出已批准的群。若钉钉和企微都有同名群，先请用户选平台；选定后将对应 `target_id` 与工作空间相对文件路径交给 `send`。专家不需要知道群的原始平台 ID。

工具是否出现在会话中由 profile 的工具集在会话开始时确定；平台开关、目标名单和文件开关则由后端在**每次发送时重新检查**。关闭开关即时阻止发送，不通过中途修改工具 schema 来实施撤权。

### 1.5 统一后端发送服务

页面的“测试发送”和专家工具的 `send` 调用同一个后端发送服务。服务端从可信运行上下文确定当前 profile，按以下顺序处理：

1. 从 `target_id` 读取所属 profile、平台、单聊/群聊类型及平台原生 ID，确认目标仍在当前 profile 的批准名单中。
2. 检查渠道启用、该平台主动沟通开启；如有文件，再检查该平台允许收发文件开启。
3. 将 `file` 作为当前 profile 工作空间的相对路径解析；解析符号链接后仍必须落在该工作空间内。核对文件存在、类型与平台大小限制。不能仅依赖 Hermes 通用媒体路径的默认校验范围。
4. 按平台分派。平台受理后记录内部 `delivery_id`、发起用户或规则、目标、文字/文件摘要、平台回执和已知状态。
5. 返回 `accepted`、`sent`、`failed` 或 `unknown`。已受理不等于对方已读；未知结果不得自动重复发送。

平台凭据只从该 profile 的配置和密钥作用域读取，不把其他 profile 或进程默认账号当成回退。行为开关属于配置，Secret 属于密钥文件；不为本功能新增非密钥 `HERMES_*` 环境变量。发送流水独立保存，MVP 不写入目标 Hermes session 历史。

### 1.6 三个平台的直接接口与 Hermes 改动

**钉钉企业应用机器人。** 用当前 profile 的 Client ID、Client Secret 获取应用 accessToken，使用当前 `robotCode`。单聊调用 `POST /v1.0/robot/oToMessages/batchSend`，群聊调用 `POST /v1.0/robot/groupMessages/send`。图片、文件按平台格式先上传取得 `media_id`，再以对应 `msgKey/msgParam` 发送。Hermes 钉钉适配器已有凭据、`robot_code` 和取 token 的基础代码，但现有 `send()` 依赖入站后临时 `session_webhook`，本地文件发送明确失败；需新增按指定目标的 OpenAPI 发送路径。不能用固定群机器人 webhook 代替企业应用机器人身份。

**飞书企业自建应用机器人。** 使用当前 profile 的 App ID、App Secret 对应的应用 `tenant_access_token`，按用户 `open_id` 或群 `chat_id` 创建消息；图片、文件上传后发送 `image_key/file_key`。Hermes `FeishuAdapter` 已有定向文字发送和本地媒体上传发送，优先复用，补产品名单校验、`open_id` 持久化和出站记录。

**企业微信 AI Bot。** 使用当前 profile 的 Bot ID、Secret 与企业微信保持 WebSocket，通过 `aibot_send_msg` 主动发文字；媒体经分片上传取得 `media_id` 后发送。Hermes 已有单聊主动文字与媒体上传发送代码。当前适配器在已识别群聊缺少 `req_id` 时提前拒绝文字发送，而企微官方 SDK 描述了无回调帧的群目标主动发送；需要用真实测试群验证当前机器人权限与平台行为后再调整。公开的 AI Bot SDK 提供消息事件和指定目标主动发送，但未提供与 `wecom-cli ... sessions list` 等价的会话列表；直连方案只能以本 profile 的已互动记录作为发现线索，结合连接状态与平台发送回执判断实际可达，不能声称发送前已从平台取得“当前可发送会话列表”。Bot WebSocket 由 gateway 进程持有，桌面等其他进程发起的工具请求必须交给该 profile 的网关连接执行，不能为同一个 Bot 再开竞争连接。

### 1.7 异常、限制与用户反馈

- **目标不明确**：返回候选平台与名称，让用户选择；不把用途说明中的命令性文字当作授权或指令。
- **目标不存在或未批准**：停止并提示先在“主动沟通”名单添加；不临时使用用户说出的原始 ID。
- **开关关闭**：明确指出是哪个平台的主动沟通或文件开关关闭，不自动换平台或机器人。
- **文件错误**：不存在、重名、越出工作空间、不支持的格式或超出限制时，不发送；专家定位后重试或请用户明确文件。
- **平台拒绝**：机器人不在群、应用权限不足、目标会话过期等错误如实返回，不改用员工个人身份发送。
- **结果未知**：保留 `delivery_id` 供查询或人工核实，不能盲目重发造成重复消息。

钉钉群聊存在平台入站限制：企业机器人可以主动向群发图片/文件，但平台文档说明群里用户无法通过 @机器人向它发送语音、视频、文件。因此“允许收发文件”不能对钉钉群聊承诺完全对称的双向能力。企业微信 AI Bot 的名单也不保证目标永久可达。

### 1.8 落地顺序与验收

1. **基础能力**：实现 profile 作用域开关、目标批准名单、用途说明、发送流水、统一后端服务和单一插件工具；使用模拟平台传输验证跨 profile、同名目标、关闭开关和文件路径限制。
2. **平台接入**：先复用飞书现有 SDK 跑通完整文字链路；补钉钉企业机器人 OpenAPI；为企微建立通向持有 WebSocket 的网关进程的发送入口，并先验证群主动发送。
3. **媒体能力**：分别验证三家的单聊/群聊图片与文件；文字说明和文件如需拆成两条消息，分别记录结果，不把部分成功报成全部成功。
4. **真实验收**：使用测试机器人和明确的测试目标，覆盖单聊、群聊、跨渠道指令、同名群、未批准目标、机器人不在群、平台权限不足、目标失效、上传失败和平台结果未知。涉及配置传播、目标解析、跨进程发送和文件 I/O 的自动化测试应走真实导入链与临时 `HERMES_HOME`，通过 `scripts/run_tests.sh` 执行。

本方案将主动发送执行器改为**后端直接调用平台机器人接口**。现有 `docs/design/1023/prd.md` §9 仍写“各平台 CLI 发送”；方案确定后需同步修订该处及相关验收文案。本章为设计稿，尚未执行真实消息发送。

## 第二章 产品设计

本章定义用户看见的页面、交互与状态。第一章定义实现约束；若两章表述有差异，以明确的平台能力边界和后端发送校验为准。

### 2.1 产品目标、使用角色与边界

一个专家对应一个 Hermes profile。专家以该 profile 绑定的企业应用机器人身份，按用户指令或已批准的任务规则向名单内人员、群发送文字、图片和文件，不使用员工个人登录态。

- **专家配置者**接入机器人、批准目标、管理开关和发送测试消息；正式服务须校验其对当前专家的管理权限。发送流水在后端保留，本期页面不提供独立记录入口。
- **指令发起者**在网页、桌面、任务对话或消息渠道会话中提出发送要求；指令不能越过名单和开关。
- **专家**确认文件与目标，必要时询问用户，再调用统一工具。专家不接触机器人凭据及平台原生目标 ID。

回复**发来指令的当前渠道会话**继续走原有回复链路，不要求主动沟通开关或目标名单。向另一会话发起新消息才属于主动沟通。仅配置机器人与名单不会触发专家无任务广播。MVP 不创建目标 Hermes session，不将主动发送写入目标会话历史，不保证发送后的目标会话连续性。

### 2.2 页面信息架构

“消息渠道”页按钉钉、企业微信、飞书切换。每个平台有独立配置，不设置跨平台总开关。页面顶部说明：**回复当前消息会话无需开启主动沟通；向其他人或群发送时，需要开启对应平台的主动沟通并批准目标。**

每个平台页依次展示：

1. **渠道接入**：机器人类型、凭据、启用开关、消息接收状态及入站相关设置。
2. **主动沟通**：能力开关、“检查配置”弹窗、可私聊的人、可发的群。两份名单在桌面宽度左右等高排列，左侧人员、右侧群；各列不足五项时随内容高度变化，超过五项时仅名单内部滚动。
3. **图片与文件**：该平台允许收发图片与文件的开关、已支持范围及平台限制。

本期页面移除“发送记录”按钮及弹窗。名单行仍显示最近测试状态；单次测试结果在测试弹窗中反馈，完整发送流水由后端保存。

“Home 会话或群 ID”属于默认结果投递，不自动加入主动沟通名单。“群聊需 @”只控制收到群消息时是否响应，不控制主动向群发送，也不是在群里 @某成员的功能。

### 2.3 开关、状态与生效规则

每个平台分别保存“启用渠道”“主动沟通”“允许收发图片与文件”。后两项默认关闭。关闭主动沟通时保留名单，但后端立即拒绝该平台新的主动发送，**包括真实测试发送**。普通文字主动发送不依赖文件开关；主动发送图片或文件要求主动沟通及文件开关同时开启。当前会话的普通文字回复仍可用。

关闭渠道时主动沟通随之关闭，目标名单和用途说明保留；重新启用渠道后须由配置者再次开启主动沟通，避免连接恢复时意外恢复对外发送。文件设置可保留，但渠道关闭期间不生效。新建或编辑名单不等于发送消息。

页面不得将以下状态合并：

- **渠道接收状态**：未配置、已停用、连接中、已连接、连接失败。
- **机器人发送条件检查**：待检查、检查中、已满足已检查前提、部分受限、检查失败。检查成功不代表每个目标此刻可达。
- **目标状态**：已批准且待实发验证、最近测试被平台受理、最近测试失败、最近测试结果未知；同时显示最近核对与测试时间。
- **单次发送状态**：平台已受理、平台确认发送、发送失败、结果未知。只有平台确有确认时才能使用“确认发送”；已受理不等于对方已读。

“检查配置”打开独立弹窗，不在主页面内联展开，也不发送消息；主动沟通关闭时仍可使用。弹窗逐项区分“已满足、待处理、待验证”，至少检查渠道启用、凭据、应用发送权限、连接条件与目标可达性；顶部概括是否有阻断项，并可重新检查。无法静态核验的权限和目标可达性必须标成“待验证”，不能因为点击检查就显示为全部通过。开启主动沟通时可以暂时没有批准目标，但页面须提示“已开启，暂无可发送目标”，不能显示成可以立即发送。钉钉、飞书的出站 API 与入站长连接不完全等同；企微 AI Bot 出站依赖相应 WebSocket。三个平台不能共用“机器人发送独立于渠道连接”的结论。

### 2.4 三个平台的添加目标入口

三家共享“核对身份 → 管理员批准 → 填用途说明 → 真实测试”的**管理结果**，不共享同一种“平台候选搜索”入口。目标发现只产生线索，批准名单由产品保存，平台实际可达性仍由发送结果判断。

**钉钉企业内部应用机器人**

- 单聊可输入并核对 `userId`；当前 profile 的机器人已收到消息且可靠取得 `sender_staff_id` 时，提供“从已有单聊选择”。若应用拥有对应通讯录权限，可查询员工并取得 ID，但通讯录命中不证明机器人有权向其发送。
- 群聊可输入并核对 `openConversationId`；机器人已收到的群消息中的 `conversation_id` 可进入“从已有群聊选择”。不能默认存在“机器人可发全部群”的统一列表。页面提示机器人须在目标群内。

**飞书企业自建应用机器人**

- 群聊在具备群信息权限时，优先从**机器人所在或可见的群**列表搜索并选择 `chat_id`；平台接口不可用或群尚未出现时，可从入站记录取得 ID，必要时手动输入并核对。
- 单聊不展示“所有机器人私聊”列表。使用入站消息中的 `open_id`，或在应用获得通讯录权限和数据可见范围后按人员查询；必要时输入 `open_id` 并核对。通讯录可见不等于机器人当前可向该人发送。

**企业微信 AI Bot**

- 不以企微 CLI 的 `sessions list` 作为本方案依赖。页面从**当前 profile 的该机器人实际收到的消息和事件**整理已互动的单聊、群聊，供配置者选择；不提供任意通讯录 `userid` 冷启动目标入口。
- 本地已互动记录不是平台实时“当前可发送会话列表”。页面显示最近互动时间并说明可达性可能变化；发送前检查本 profile 的机器人连接及记录，最终以平台回执或错误判断。

两个添加弹窗共用紧凑结构：**标题与当前机器人 → 添加方式 → 目标信息或候选搜索 → 用途说明与核对确认 → 取消/批准加入名单**。有候选时默认展示“从已有单聊选择”或“从已有群聊选择”，没有候选且平台允许手填时默认展示 ID 输入；企微 AI Bot 只提供已互动候选，不提供任意通讯录 ID 冷启动。批准与测试分为两步，弹窗不放“批准并测试”按钮。

候选列表按姓名/群名或完整原生 ID 搜索；每条展示平台显示名称、尽可能完整的 ID、最近互动时间。ID 过长时只在视觉上截断，悬停和详情可读全值。单条高度尽量紧凑，当前原型按约 48px 设计；最多显示四条，第五条起在候选区内部滚动。已经批准的候选仍显示“已加入名单”，但不可重复选择或批准。候选数为零时在列表区域给出首次发现步骤与手填入口；搜索无匹配时提供清空搜索。飞书群在具备权限时可刷新机器人可见群。所有候选都只是发现线索，不能标为“当前可发送”。

### 2.5 添加、批准与维护目标

添加目标的通用交互为：选择已有会话或输入原生 ID → 核对平台显示名称、目标类型、完整 ID、来源及最近互动时间 → 填写**用途说明（选填）** → 管理员勾选核对确认并批准加入名单 → 在名单中单独测试。钉钉、飞书手动输入须核对 ID 对应的身份与当前机器人的适用范围；钉钉群还须确认机器人在目标群内。保存目标不发送平台消息，批准后初始状态为“已批准 · 尚未验证”。

平台显示名称与用途说明分别保存。人员用途示例为“负责设备维护与停机协调”，群用途示例为“用于产线异常协同”；MVP 不设独立别名字段。用途说明是可编辑的资料，不是对专家的指令。同一 profile、平台、类型、原生 ID 不得重复加入；同名目标可以并存。

人员和群分区展示。名单行显示平台名称、选填用途说明、批准状态和最近测试状态，并提供查看详情、测试、移除；候选来源、最近互动与最近核对时间放在详情中，避免名单行拥挤。详情可编辑用途说明、弱化展示并复制原生 ID；不把原生 ID 当作主要名称。移除后后端立即拒绝新发送，但无法撤回已被平台受理的消息。搜索名单只帮助管理员查找，不改变发送权限。

### 2.6 不发送消息的条件检查

“检查配置”在独立弹窗中逐项展示已检查的前提和无法静态确认的事项：当前 profile 的机器人凭据、应用发送权限、必要的连接与平台设置等。状态分别为“已满足、待处理、待验证”，支持重新检查，关闭弹窗不改变渠道开关。不能只返回“已检查”并使用绿色成功样式。无法由静态检查判断的目标可达性，明确标注“需实际发送验证”。企微的本地历史互动名单尤其不能标为平台当前可发送名单。

### 2.7 真实测试发送

名单中的“测试”会向目标**真实发送消息**，与专家工具复用同一后端发送服务。渠道未启用、主动沟通关闭、目标未批准时禁止真实测试；图片或文件测试还需文件开关开启。配置者可先保存目标，待开启主动沟通后再测试。

测试弹窗展示平台、机器人身份、目标名称与类型、原生 ID 尾部、测试内容。文字输入始终可见，可附带一张图片或一个文件；MVP 每次最多一个附件。附件从当前专家工作空间选择，或先上传到工作空间再选择。点击发送前提示“将向真实目标发送”，避免把配置检查与发消息混为一谈。

结果展示发送时间、平台回执和内部 `delivery_id`。平台已受理不等于已送达或已读；失败给出具体原因；结果未知时提示可能已经发出，不自动重试。文字与附件需拆成两条消息时分别记录结果，部分成功不得整体报为成功。

### 2.8 专家调用与用户指令流程

产品只向专家暴露第一章定义的一个 `proactive_message` 工具，包含 `list_targets` 和 `send` 两个 action。三个平台由后端分派；页面不要求普通用户认识工具名或平台原生 ID。工具列表在会话开始时确定，后端开关和名单则每次发送时即时生效。

示例指令：“把工作空间里的本周质检报告发到产线协作群。”专家按以下顺序处理：

1. 使用已有文件能力确认报告的唯一文件及工作空间相对路径；文件同名或不明确时先询问。
2. 调用 `list_targets` 获取当前 profile 已开启主动沟通的平台中的已批准群；名单较短时可先列全量，避免查询词过窄漏掉目标。
3. 根据用户原话、平台、名称及用途说明判断。跨平台同名、多个合理匹配或匹配牵强时向用户列出候选并询问，不默认第一个。
4. 目标唯一明确时调用 `send(target_id, text?, file?)`。模型不给出原生 `chat_id`、机器人凭据或 profile。
5. 后端重新检查批准状态、开关、文件路径与平台能力，再执行发送。专家在**发来指令的原会话**报告结果；目标侧不自动产生新的 Hermes session。

用户若只要求专家回复当前消息会话，直接走原渠道回复链路，不执行名单查询。仅用户指令或已批准规则可以触发新的主动发送；用途说明中的命令性文字不得视作新指令。工具集在会话开始时装载，新安装插件可能需要新会话才显示；但已装载工具的旧会话仍受后端即时撤权约束。

### 2.9 文件与图片的处理

页面文件开关在 MVP 只承诺已验证的图片和文件，不以“语音、视频”概括未实现的能力。当前会话的入站附件处理和向名单目标发附件均受该开关控制；主动向名单发送还须开启主动沟通。钉钉群聊的入站文件限制单独说明，不推断企业机器人无法主动发文件。

专家发送的文件必须位于当前 profile 工作空间内。页面测试如需使用本机文件，先上传至专家工作空间，再由统一发送服务按工作空间文件处理。上传、平台媒体上传、文字发送和附件发送可能是不同步骤；发送记录区分每一步的失败和部分成功。平台类型、大小与格式限制以对应渠道的实际能力校验，不用三个平台共同的无依据固定限制。

### 2.10 发送记录与反馈

发送流水仍由后端独立保存，至少包含当前专家、机器人、目标、发起人或任务、文字或文件摘要、发送时间、`delivery_id`、平台回执及已知结果，供故障排查和后续审计使用；不得保存凭据，也不应在默认页面铺开敏感正文。**本期“消息渠道”页不提供发送记录按钮、筛选列表或弹窗**。配置者从测试结果和名单行的“上次测试”了解最近状态；该历史状态不能代替当前可达性判断。未来若增加审计页面，再定义按平台、目标、时间、状态和发起来源筛选的权限与脱敏规则。

用户可理解的错误反馈应覆盖：目标未批准或已移除、目标有多个合理匹配、指定平台开关关闭、文件不存在或越出工作空间、文件格式或大小不支持、机器人不在群或权限不足、企微历史会话失效、平台上传失败、结果未知。错误消息指出具体平台和目标，不自动改用其他机器人、个人身份或名称相近目标。结果未知保留查询线索，避免盲目重发。

### 2.11 权限与安全

配置、批准名单和测试发送需要当前专家的管理权限；机器人凭据和目标名单按 profile 隔离。后端从可信运行上下文确定 profile，不能接受模型或页面表单伪造其他 profile。产品 `target_id` 与原生平台 ID 分开；原生 ID 只由后端读取。目标显示名称、历史消息和用途说明均是不可信资料，不得提升为授权或系统指令。

名单批准、关闭开关、删除目标和文件校验都由后端在发送时执行，前端禁用按钮不能替代后端拒绝。文件路径解析符号链接后仍须留在当前工作空间。测试发送与专家发送都留下可追踪记录。

### 2.12 MVP 验收场景

1. 钉钉单聊输入并核对 `userId`，钉钉群输入并核对 `openConversationId`；历史互动快捷项可选，但不出现“所有机器人可发群”的虚构列表。
2. 飞书群可在具备权限时从机器人可见群选择；人员使用入站 `open_id` 或有权限的通讯录查询。权限不足时提供明确降级入口和说明。
3. 企微展示当前 profile 的机器人已互动会话，注明历史记录不保证当前可达；任意通讯录 `userid` 不能直接获批。
4. 从网页任务向钉钉单聊发送文字、向群发送工作空间文件；从飞书会话 A 下指令向飞书或企微会话 B 发送，给 A 的普通回复不受名单限制。
5. 两个平台存在同名群时专家询问平台；未批准目标、跨 profile `target_id`、关闭开关均被后端拒绝。
6. 文件开关关闭时允许主动发文字而拒绝主动发图片和文件；不存在、同名不确定、越出工作空间及超平台限制的文件都不得发送。
7. 机器人不在群、企微历史会话失效、平台权限不足、上传失败及结果未知都有准确反馈；后台发送流水区分已受理、失败、未知和部分成功。

## 第三章 离线原型交付规格

原型仓库为 `D:/CodingWorkSpace/IndustryAgentPlatform/专家`，主组件为 `src/demo/components/ExpertChannelTab.vue`，候选数据位于 `src/demo/channel-target-fixtures.js`，样式位于 `src/demo/styles.scss`。本章规定研发评审时**界面呈现的最终产品效果**。候选、检查和发送结果仍由本地固定数据与交互生成，不接入真实平台，也不调用真实发送接口；这一边界写在源码和研发说明中，界面主体不重复出现“模拟”“演示”等原型提示词，不得拿原型结果证明实际权限或送达。

### 3.1 渠道与名单页面

1. 钉钉、企微、飞书分别显示“企业内部应用机器人”“AI Bot”“企业自建应用机器人”。钉钉凭据标为 Client ID、Client Secret，Robot Code 与 Client ID 不同时可选填；钉钉隐藏“扫码配置”，企微和飞书保留各自入口。
2. “启用渠道”“主动沟通”“允许收发图片与文件”按平台独立。关闭渠道同时关闭主动沟通但保留名单；重新启用不自动恢复主动沟通。Home 仅用于默认结果投递，群聊需 @ 仅影响入站响应。
3. “可私聊的人”和“可发的群”在桌面宽度同一行、两列等高；少于五项时高度随较长一列变化，超过五项各列内部滚动。名单行以名称、选填用途、批准与最近测试状态及操作为主，不铺开旧版来源占位文案。未测试为中性灰；“已受理、发送失败、结果未知、部分成功”是不同状态，不表示此刻一定可达。
4. 保留目标详情、用途说明编辑、复制原生 ID、测试与移除确认。点击“检查配置”打开独立弹窗，逐项显示“已满足、待处理、待验证”，提供重新检查；主页面不内联铺开检查项。本期**不显示“发送记录”按钮或弹窗**。

### 3.2 添加可私聊的人与可发的群

两个弹窗共用：**标题及当前机器人 → 添加方式 → 手填字段或已有会话候选 → 用途说明及核对确认 → 取消/批准加入名单**。批准与测试分步进行，底部不放“批准并测试”。

- 钉钉人员提供“输入 userId 并核对”“从已有单聊选择”；群提供“输入群 ID 并核对”“从已有群聊选择”。有候选时打开即显示已有会话；没有候选时默认手填。飞书按 `open_id` / `chat_id` 区分字段，企微只允许从当前机器人已互动会话选取。
- 手填时人员录入 `userId` 与平台显示名称，群录入 `openConversationId` 与群名称；两者均可填写用途说明。人员确认“已核对人员身份及当前应用的适用范围”，群确认“已核对群身份，且确认当前机器人在目标群内”。ID 或名称变化后重新确认。
- 已有会话支持按名称或完整 ID 搜索。候选行显示名称、尽可能完整的 ID 和最近互动时间；行高约 48px，最多显示四条，第五条起在候选区内滚动。超长 ID 可视觉截断，但悬停和目标详情可查看完整值。选中后显示完整 ID 摘要，再填写用途与确认。
- 已加入名单的候选仍可见，并标明“已加入名单”，但不可再次选择；去重以当前专家、平台、类型及原生 ID 为准。无候选时给出首次发现步骤与手填入口；搜索无匹配时可清空搜索。历史互动与通讯录结果只提供发现线索，不证明当前机器人可发送。

### 3.3 测试、文件与结果文案

1. “测试”弹窗显示平台、机器人、目标类型与名称、原生 ID、文字和最多一个工作空间图片或文件。文件开关关闭时仍可填文字，附件选项禁用。钉钉图片不以公网 URL 作为默认流程。
2. 文件开关只承诺图片与文件，不概括语音、视频；单独说明钉钉群成员通过 @机器人发送语音、视频、文件的入站限制。“按 Markdown 发送”和主动 @指定成员不进入本期主流程。
3. 名单、详情与单次结果使用最终产品文案：“已批准 · 尚未验证”“上次测试已受理”“发送失败”“结果未知”“部分成功”。已受理不等于已送达或已读；未知结果不自动重试。原型内的旧浏览器数据须映射成这些文案，不能泄漏“历史模拟已受理”等提示词。
4. 单次结果仍呈现时间、回执与 `delivery_id`；发送流水可留在本地状态或后端设计中，但当前页面不出现发送记录入口。主动沟通区给出从工作空间找文件、查询已批准目标、同名群先询问平台的使用示例。

### 3.4 候选样例与旧数据兼容

候选样例按专家、平台和机器人身份隔离。原型为每个专家的钉钉、飞书、企微分别提供可搜索的人员与群聊样例；钉钉各五条用于同时检查搜索和“四条可见、更多滚动”。已有名单中的候选仍显示但不可重复批准。示例覆盖未验证、已受理、失败、未知及部分成功；本地样例状态不代表真实平台回执。浏览器旧数据升级时补齐已知样例，不覆盖用户自行添加的目标或已有结果。

### 3.5 原型验收

1. 在 `/experts/` 切换专家和三个平台，名单、候选、机器人名称、配置检查及测试弹窗不串用；切换时旧平台弹窗关闭。
2. 分别检查人员和群聊手填、已有会话搜索、候选选中、完整 ID 展示、已加入名单不可重复选取、空状态与四条以上候选滚动；桌面和窄屏均可完成核对与批准。
3. 关闭渠道或主动沟通后不能测试；重新启用渠道不自动开启主动沟通；文件开关关闭时仅可测试文字。“检查配置”弹窗不发送消息，阻断与待验证状态清楚区分。
4. 消息渠道功能区没有发送记录按钮或弹窗，列表与单次结果没有“模拟”“演示”字样。运行原型项目 `npm test`、`npm run build`，并手动检查主页面及上述弹窗。Hermes 源码若实施改动，测试遵循其 `scripts/run_tests.sh`。
