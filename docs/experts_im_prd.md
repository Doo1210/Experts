# 专家消息渠道与主动沟通 PRD

状态：设计方案  
适用范围：Hermes 专家（Profile）· 钉钉、企业微信 AI Bot、飞书消息渠道  
整理依据：同目录 `IM_prd.md` 及专家管理页当前原型

**阅读路径**：后端研发重点阅读第一章，并在第二章各功能下查看“Hermes 依据”和“需实现”；前端研发重点阅读第一章的场景流程，以及第二章的“产品交互”和状态反馈。第一章只定义一次业务规则，第二章按页面从上到下描述，不重复定义发送权限。

## 第一章 整体实现方案与场景业务逻辑

### 1.1 目标、角色与 MVP 边界

一个专家对应一个 Hermes profile。专家只以**当前 profile 绑定的企业应用机器人身份**接收、回复和主动发送消息，不借用员工个人 OAuth 登录态，也不调用钉钉、飞书或企微 CLI 完成发送。

- **专家配置者**配置渠道、核对并批准人员和群、管理开关、发送测试消息。
- **指令发起者**在网页、桌面、任务对话或消息渠道中提出跨会话发送要求；已批准的定时任务或业务规则也可触发。
- **专家**确认唯一文件和唯一目标，必要时向用户追问，再调用统一工具。

“主动沟通”特指**向发来指令的当前会话以外，发起一条新消息**。入站消息和对当前会话的普通回复走既有渠道链路，不受主动沟通名单约束。开启开关和添加名单本身不构成广播指令。

MVP 不为目标创建新的 Hermes session，不镜像主动发送到目标会话历史，也不保证发送后的目标侧回复自动接续原任务。发送结果进入独立流水，用于本次反馈、排障和后续审计；本期“消息渠道”页不提供独立的发送记录按钮或弹窗。

### 1.2 核心对象与总体链路

以下对象应分开保存和判断：

- **渠道配置**：当前 profile、平台、机器人身份、凭据引用、渠道启用状态、主动沟通开关、图片与文件开关及入站设置。Secret 留在该 profile 的密钥作用域，行为开关属于配置。
- **已有会话线索**：从当前机器人处理过的入站事件或有权限的平台查询得到；含平台原生 ID 及类型、显示名称、来源、最近互动时间、profile 和机器人身份。它只是供管理员核对的候选，不是发送授权。
- **已批准目标**：产品生成不透明 `target_id`，绑定 profile、平台、机器人、人员/群类型、原生目标 ID、显示名称、选填用途、批准人与时间、最近核对及测试结果。模型只看到 `target_id` 和必要的描述，不拿到原生 ID 或凭据。
- **发送流水**：独立的 `delivery_id`、发起用户或规则、目标、文字/文件摘要、时间、平台回执、分步结果和已知状态。平台“已受理”不等于送达或已读。
- **Hermes session**：承载入站对话及回复路由；`session_id`、session key、目录展示名均不是主动发送目标，也不能证明机器人当前可达。

总体链路为：**入站收集目标线索 → 配置者核对并批准 → 专家列出已批准目标 → 识别唯一目标与文件 → 统一服务按可信 profile 再次校验 → 按平台发送 → 返回结果并保存流水**。页面测试发送与专家工具发送应进入同一个后端服务；前端禁用按钮不能替代服务端拒绝。

### 1.3 渠道接入与当前会话回复

配置者为每个平台绑定当前 profile 的机器人凭据并启用渠道。企微使用 AI Bot，钉钉使用企业内部应用机器人，飞书使用企业自建应用机器人。渠道连接状态只表示接收入站消息的条件，不表示名单目标可以主动发送。Home 会话只用于默认结果投递，不自动加入允许名单；“群聊需 @”只决定收到群消息后是否响应，不决定专家能否主动发群。

用户在当前渠道会话发消息后，适配器产生入站事件，Hermes 路由到该 profile 的 session，专家仍通过既有回复链路答复这个会话。若图片与文件开关关闭，普通文字继续处理；入站图片和文件不交给专家使用，应给出清楚的受限反馈。钉钉群里成员通过 @机器人发送语音、视频和文件存在平台入站限制，不能把文件开关表述为对该场景的完全双向保证。

### 1.4 目标发现、核对与批准

每个 profile、每个平台分开维护“可私聊的人”和“可发的群”。候选由当前机器人身份下的入站观察或平台允许的查询产生，管理员确认身份、稳定平台 ID、机器人适用范围后批准。同名目标可并存；同一 profile、平台、类型及原生 ID 不得重复批准。保存名单**不发送消息**；批准后先显示“已批准 · 尚未验证”，由单独测试确认实际发送结果。

三家发现方式不同：钉钉人员可手填并核对 `userId`，入站 `sender_staff_id` 可形成单聊线索；群可手填并核对 `openConversationId`，入站群 `conversation_id` 可形成群线索。飞书人员使用当前应用可用的 `open_id`，来源是入站事件或有权限的通讯录查询；群优先从有权限的机器人可见群取得 `chat_id`，必要时手填核对。企微 AI Bot 只从该机器人已互动的单聊和群聊形成候选，不接受任意通讯录 `userid` 冷启动。以上线索都不等于平台实时可发送列表。

### 1.5 主动发送文字、测试与规则触发

用户要求从网页、任务或消息会话 A 向目标 B 发送时，专家先调用 `list_targets` 获取当前 profile 已开启主动沟通的平台中的批准目标。用平台、类型、名称、用途和用户原话判断；跨平台同名、多个合理匹配、文件不唯一或匹配牵强时先询问，不默认第一项，也不使用用户临时说出的原始 ID 绕过名单。唯一明确后调用 `send(target_id, text?, file?)`。完成后在**发来指令的原会话**报告结果，目标侧不自动创建 Hermes session。

名单中的“测试”是真实产品中的发送动作：渠道未启用、主动沟通关闭或目标未批准时不得测试；仅保存目标后可以稍后再测。检查配置只是静态条件检查，不能替代测试，也不能向平台发送。定时任务或业务规则触发时，沿用同一 `target_id` 与发送服务，不得因无人实时操作而省略开关、批准及文件校验。

### 1.6 图片与文件收发

“允许收发图片与文件”按平台独立，默认关闭。它控制当前渠道会话的入站图片/文件处理，以及向批准目标发送附件；普通文字回复和文字主动发送不依赖该开关。主动向名单目标发附件必须同时满足**渠道启用、主动沟通开启、目标已批准、文件开关开启**。一次发送最多带一个工作空间文件，可同时带文字；如果平台需要分步发送文字和附件，应分别记录结果，部分成功不能报为全部成功。

专家先用现有文件能力确定当前 profile 工作空间内的唯一相对路径。服务端解析符号链接后仍须保证路径位于该工作空间，核对存在性、类型、平台格式及大小限制；上传失败则不得假报发送成功。本机文件用于页面测试时须先进入专家工作空间，再按统一发送服务处理。钉钉图片不以公网 URL 作为默认用户流程。

### 1.7 统一工具、服务端校验与结果状态

通过 profile 作用域插件注册一个位于独立工具集 `proactive_messaging` 的 `proactive_message` 工具，而非增加 Hermes core 工具。它只有两个 action：

- `list_targets(kind?, platform?, query?)`：省略平台时可列出当前 profile 中主动沟通已开启渠道的批准目标；返回 `target_id`、平台、类型、名称、选填用途和必要状态，不返回原生目标 ID 或凭据。
- `send(target_id, text?, file?)`：文字和文件至少有一项，文件最多一个；不接受模型传入的 profile、机器人凭据或原生 `chat_id`。工具集在会话开始时装载，后端每次发送仍重新读取开关和名单，关闭开关即时撤权。

统一服务按顺序执行：① 从可信运行上下文确定 profile，按 `target_id` 查当前 profile 的批准记录；② 检查渠道、主动沟通及必要的文件开关；③ 校验工作空间文件；④ 用该 profile 的机器人身份按平台分派；⑤ 记录 `delivery_id` 与分步回执；⑥ 返回 `accepted`、`sent`、`failed`、`unknown`，或文字/附件组合发送的整体 `partial`。只有平台明确确认时才用 `sent`；`unknown` 保留核实线索，不自动重试。

### 1.8 平台接入、异常与交付验收

- **钉钉**：使用当前 profile 的 Client ID、Client Secret 和必要时单独配置的 Robot Code 获取应用 token；单聊按 `userId` 调 `POST /v1.0/robot/oToMessages/batchSend`，群按 `openConversationId` 调 `POST /v1.0/robot/groupMessages/send`，媒体先上传再发。现有适配器的 `send()` 依赖有期限的入站 `session_webhook`，不足以完成跨会话主动发送；不能以固定群 webhook 冒充当前企业应用机器人。接入时复核官方接口契约。
- **飞书**：使用当前应用身份及 `tenant_access_token`，创建消息时单聊采用 `receive_id_type=open_id`、群采用 `receive_id_type=chat_id`；图片和文件取得 `image_key` / `file_key` 后发送。优先复用现有定向文字和本地媒体上传能力，但要补 `open_id` 的可靠持久化、批准名单校验和发送流水。
- **企微 AI Bot**：复用当前 profile 持有的 WebSocket，通过 `aibot_send_msg` 指定目标发送，不能为同一 Bot 再开竞争连接。现有代码在已识别群聊缺少 `req_id` 时拒绝发送；群主动发送是否可行须用测试机器人和真实群验证，再决定适配器调整。

目标未批准、开关关闭、机器人不在群、权限不足、历史会话失效、文件越界或上传失败时，返回具体平台与目标的失败原因，不换用其他机器人或个人身份。MVP 先用可控传输验证跨 profile、重名目标、撤权和文件边界；再逐平台验收单聊、群聊、图片、文件及未知/部分成功。涉及 Hermes 源码的自动化测试使用其 `scripts/run_tests.sh` 和临时 `HERMES_HOME`。

## 第二章 产品设计与 Hermes 接入说明

本章按“消息渠道”页从上到下排列。每项区分**产品交互、Hermes 依据、需实现、验收**；字段和源码路径指向 Hermes 源仓库，原型展示规则以本仓库 `src/demo/components/ExpertChannelTab.vue` 为参照。第二章中的后端接口名是待落地的**能力语义**，不是现有 HTTP 路由。

### 2.1 页面总览与平台切换

**产品交互**

页面说明：“接入钉钉、企业微信和飞书机器人。回复当前会话无需主动沟通；向其他人或群发送须开启主动沟通并批准目标。”平台切换区按渠道分别显示连接状态。选中平台后依次展示：**渠道接入 → 主动沟通与名单 → 允许收发图片与文件 → 命令提示**。桌面与窄屏可用；切换专家或平台时关闭旧平台的添加、详情、检查及测试弹窗，未保存草稿不串到新平台。

**Hermes 依据与需实现**

`gateway/config.py` 的平台配置及 `gateway/platforms/base.py` 的 adapter 是渠道基础；`gateway/session.py` 的来源字段和 profile 路由负责入站隔离。产品层需要按可信 profile 返回该平台的机器人类型、连接状态、开关和名单，不把进程默认账号当作其他专家的配置。页面不依据名单或检查状态推断“已连接”。

**验收**：三个平台及两个专家来回切换，配置、名单、候选、开关和弹窗不串用。

### 2.2 渠道接入卡片

**产品交互**

- 企微显示“AI Bot · 仅对已有会话主动发送”，凭据为 Bot ID、Bot Secret。点击“扫码配置”打开弹窗：标题为“扫码配置企业微信 AI Bot”，桌面端左侧为二维码、右侧为扫码说明和“在新窗口打开二维码”，窄屏改为上下排列；二维码随窗口高度缩放，弹窗内容一屏展示且不在二维码区域内滚动；关闭弹窗不改变连接状态。
- 钉钉显示“企业内部应用机器人”，凭据为 Client ID、Client Secret；Robot Code 与 Client ID 不同时选填，不显示“扫码配置”。
- 飞书显示“企业自建应用机器人”，凭据为 App ID、App Secret，不显示“扫码配置”。扫码入口仅企微保留。
- “启用渠道”控制持续接收和回复。关闭后连接状态变为未连接、主动沟通关闭，但名单保留；再次启用不自动开启主动沟通。渠道接入卡片不展示 Home 会话或群 ID 配置项。“群聊需 @”只影响入站群消息响应。

连接状态使用未配置、已停用、连接中、已连接、连接失败等真实状态。保存配置而未启用时不得显示已连接；凭据只显示“已配置”占位，不在页面回显 Secret。

**Hermes 依据**：`gateway/config.py` 的 `PlatformConfig` 与各平台 adapter 配置；钉钉 `plugins/platforms/dingtalk/adapter.py` 读取 Client ID、Client Secret 与 `robot_code`，飞书 `plugins/platforms/feishu/adapter.py` 使用 App ID、App Secret，企微 `plugins/platforms/wecom/adapter.py` 使用 Bot ID、Secret 建立 WebSocket。

**需实现**：按 profile 安全读写渠道行为配置和密钥；企微扫码弹窗所需二维码及授权结果由服务端提供，前端不能把弹窗打开或二维码加载视为连接成功；提供连接状态与失败原因，区分配置已保存、接收连接成功、出站发送条件已检查。关闭渠道时即时关闭该平台的主动发送能力。

**验收**：三家凭据字段正确，仅企微显示扫码配置；点击后弹窗完整显示二维码及操作，关闭后状态不变；渠道接入卡片不显示 Home 会话或群 ID；关闭渠道后名单不丢失，重新连接不自动恢复主动沟通。

### 2.3 主动沟通开关与“检查配置”弹窗

**产品交互**

主动沟通默认关闭，只允许当前机器人向该平台批准名单中的**其他**会话发起新消息。渠道未启用或未连接时不能表现为“已可发送”；开关开启但名单为空时显示“暂无已批准的可发送目标”。关闭主动沟通后保留名单，测试发送也不可进行；当前会话的正常回复不受影响。

卡片顶部并列展示独立的“发送条件检查”摘要与“检查配置”入口。点击后打开弹窗，不在主页面内联铺开。弹窗列出渠道启用、机器人凭据、应用发送权限、连接条件、目标可达性；每项区分“已满足、待处理、待验证”，顶部指出阻断项并提供“重新检查”。配置检查**不发送消息**，静态无法确认的应用权限和目标可达性标为待验证，不因点击按钮而全绿。

**Hermes 依据**：渠道 adapter 的连接/凭据状态只覆盖一部分前提；`gateway/session.py` 的来源和 `gateway/channel_directory.py` 的目录不能证明目标此刻可发送。企微出站依赖当前 Bot WebSocket，钉钉和飞书的出站 API 权限与入站连接还须分开判断。

**需实现**：提供按 profile、平台的发送条件检查能力，返回每项 `status`（满足、阻断、待验证）、简明原因及整体摘要；每次发送仍由后端重验开关和目标，不把检查结果当长期授权。

**验收**：未启用、缺凭据、连接失败及静态无法确认的情况分别显示正确状态；关闭弹窗不改变任何开关，也不发送消息。

### 2.4 可私聊的人、可发的群与添加弹窗

**产品交互：名单及维护**

“可私聊的人”在左，“可发的群”在右，桌面宽度两列等高；少于五项时随较长一列自适应，超过五项各自内部滚动，窄屏改为纵向排列。名单行以名称、选填用途、批准/最近测试状态和“详情、测试、移除”为主；未测试为中性灰，不在列表铺开旧版来源占位文字。详情展示来源、最近互动、最近核对、完整原生 ID 及可编辑用途。移除需确认。

**产品交互：添加人员与群**

两个弹窗共用“当前机器人 → 添加方式 → 目标信息/候选搜索 → 用途说明 → 身份核对确认 → 批准加入名单”。有候选时默认展示“从已有单聊选择”或“从已有群聊选择”；无候选且平台允许手填时默认输入 ID。钉钉人员手填 `userId` 与平台显示名称，群手填 `openConversationId` 与群名称；飞书改用 `open_id` / `chat_id`。企微 AI Bot 不提供任意通讯录 `userid` 冷启动入口。人员与群使用不同核对确认文案，ID 或名称变化后要求重新确认。批准与测试分两步，弹窗底部只有取消、批准加入名单。

已有会话按名称或完整原生 ID 搜索。候选行高约 48px，最多显示四条，更多条目在候选区内部滚动；尽可能显示完整 ID，过长时视觉截断并提供完整值。最近互动时间与名称同列展示。已在名单中的候选仍显示“已加入名单”但不可重复选择。无候选时给出首次发现步骤，搜索无匹配时可清空搜索。候选只表示当前机器人的已知线索，不标成“当前可发送”。

**Hermes 依据**

- 通用 `gateway/session.py` 的 `SessionSource` 有 `platform`、`chat_type`、`chat_id`、`user_id`、`user_id_alt` 与可选 profile；新 session 来源进入 `origin_json`。既有 session 的 origin 可能是创建时快照。`gateway/channel_directory.py` 只产出 ID、名称、类型等目录项，还可能包含人工别名占位，不能直接用于批准。
- 钉钉 `plugins/platforms/dingtalk/adapter.py`：群入站 `conversation_id` 对应群目标线索；单聊 `sender_staff_id` 到 `user_id_alt` 时可作为 `userId` 候选。单聊 `chat_id` 可能是 `conversation_id`，不能直接填入人员 ID。
- 飞书 `plugins/platforms/feishu/adapter.py`：群入站提供 `chat_id`；发送者主 ID 优先使用 `user_id`，无此值才使用 `open_id`，所以需要在入站处单独保存当前应用的 `open_id`。机器人可见群查询还取决于平台权限。
- 企微 `plugins/platforms/wecom/adapter.py`：DM 使用发送者 `userid`，群使用 `chatid`。本地已互动来源不保证仍可达；当前群发送代码缺少缓存 `req_id` 时会拒绝，须专项验证。

**需实现**：在入站事件处建立按 profile、平台、机器人身份隔离的候选观察记录，保留**原生 ID 类型和值、显示名、来源与最后互动时间**。单独提供候选搜索与管理员批准接口；批准后生成不透明 `target_id`。服务端按 profile、平台、类型、原生 ID 去重；相同显示名可共存。名称、用途及历史消息均为不可信资料，不得成为授权或给专家的指令。

**验收**：三家人员/群 ID 不混用，候选与已批准目标分开；同名可并存、重复 ID 被拒绝；切换专家不串名单，旧浏览器数据升级不覆盖用户自建目标。

### 2.5 测试发送与单次结果

**产品交互**

配置者从已批准名单行打开“测试”。弹窗显示平台、机器人身份、目标名称及类型、原生 ID、文字输入和最多一个工作空间图片或文件。文字始终可填，附件可不选；没有文字时附件必选。文件开关关闭时文字仍可测试，附件选项不可选。点击前清楚显示目标和发送者，正式产品提示“将向目标发送测试消息”。

单次结果区分“平台已受理、平台确认发送、发送失败、结果未知、部分成功”，展示发送时间、平台回执和内部 `delivery_id`。失败说明机器人不在群、权限不足、目标会话失效、上传失败等具体原因；未知结果提示可能已发出，不能自动重试。名单行只显示最近测试状态和时间，不把历史结果当当前可达性。当前页面不提供独立发送记录入口。

**Hermes 依据**：飞书 `plugins/platforms/feishu/adapter.py` 已能按 `open_id` 或 `chat_id` 创建消息并有部分媒体上传发送能力；钉钉 `plugins/platforms/dingtalk/adapter.py` 的现有 `send()` 主要依赖临时 `session_webhook`；企微 `plugins/platforms/wecom/adapter.py` 可按目标发文字，但群缺少 `req_id` 的行为需验证。各平台现有 `SendResult` 不能代替产品层的批准、文件和流水校验。

**需实现**：测试与专家工具共用第一章的统一发送服务，后端重新检查可信 profile、目标批准及开关，不接受前端传入的机器人凭据或其他 profile。文字和附件分步发送时返回各部分结果及整体状态，不把部分成功合并为成功。

**验收**：未连接、主动沟通关闭、目标未批准时不能测试；结果未知留有查询线索且不自动再发；列表、详情和弹窗的状态措辞一致。

### 2.6 允许收发图片与文件

此卡片位于主动沟通及名单卡片之后，是**独立功能与独立开关**，不能埋在测试弹窗规格中。

**产品交互**

开关按平台保存，默认关闭，标签为“允许收发图片与文件”。说明文件保存在当前渠道对话工作目录；向名单目标发送附件还须开启主动沟通。关闭时普通文字入站、当前会话回复和主动文字发送仍可用，入站图片/文件处理及主动附件发送受限。钉钉群需单独注明：群成员通过 @机器人无法向其发送语音、视频和文件；不得据此推断企业机器人不能主动向群发文件。MVP 不用该开关承诺语音和视频能力。

**Hermes 依据**：`gateway/platforms/event.py` 的 `MessageEvent` 带入站媒体引用，`gateway/platforms/base.py` 处理消息与附件交付，各平台 adapter 实现媒体解析、下载及部分 `send_image_file` / `send_document` 能力。飞书已有本地媒体上传路径；钉钉现有本地文件发送路径不满足企业应用机器人定向发送；企微媒体使用 Bot WebSocket 与媒体上传流程。工作空间由当前 profile 作用域确定，不能仅依赖通用媒体路径默认范围。

**需实现**：在入站附件进入专家工作空间或提供给模型前检查文件开关；在出站媒体上传前再次检查渠道、主动沟通、批准目标及文件开关。解析工作空间相对路径及符号链接，按平台能力校验大小、格式和媒体类型。若文字与附件拆成两条消息，保存分步结果并对外报告部分成功。

**验收**：关闭文件开关仍可收发文字，不能处理入站附件或向名单发附件；开启文件开关而主动沟通关闭时，当前会话附件能力按渠道规则可用，但不能向名单主动发附件；不存在、越出工作空间或超出平台限制的文件不得发送。

### 2.7 命令提示与辅助说明

**产品交互**：页面末尾提示 `/help`、`/new`、`/stop`、`/sethome`、`/status` 等可用命令；钉钉和飞书群在要求 @ 时说明使用方式。主动沟通卡片示例：“把工作空间里的质检报告发到产线协作群。”说明专家先确认文件、再找已批准目标，跨平台同名群会询问平台。明确回复当前消息会话无需主动沟通。

**Hermes 依据与需实现**：命令交由现有渠道入站与 slash command 链路处理；提示文案应由当前平台和群聊需 @ 设置决定，不改变工具 schema、批准状态或发送权限。

### 2.8 前后端能力契约与研发改动清单

以下是建议的服务能力语义，具体 URL、存储表及传输形式由实现设计确定：

1. **读取/保存渠道配置**：返回当前 profile 的平台、机器人类型、凭据是否已配置、启用/连接状态、主动沟通、图片文件开关、Home、群聊需 @；保存 Secret 时仅写密钥作用域，不回显原值。
2. **检查发送条件**：按当前 profile 和平台返回整体摘要及逐项状态、原因；静态无法确认的权限和目标可达性标为待验证。此能力不触发发送。
3. **查询已有会话候选**：按当前 profile、机器人身份、平台、人员/群类型及名称/ID 关键词查找，返回候选原生 ID 及类型、名称、来源、最近互动、是否已批准。候选不含发送授权，也不把人工别名占位当平台验证结果。
4. **批准/维护目标**：批准时由服务端生成 `target_id`，记录管理员、时间、原生 ID、用途及所属机器人；提供更新用途、移除和查询名单能力。移除或关闭开关后立即拒绝新的发送。
5. **测试与专家发送**：服务端从可信运行上下文确定 profile，请求只给出 `target_id`、可选文字和一个工作空间相对文件路径；返回整体状态、必要的分步结果、`delivery_id`、平台回执摘要和用户可理解的失败原因。

Hermes 现有来源和 adapter 只覆盖上述能力的部分字段。需新增入站目标观察存储、管理员批准名单、按 profile 的发送配置与密钥读取、统一发送服务、工具集 `proactive_messaging` 及 `proactive_message` 两个 action；平台定向发送与媒体能力按第一章逐个补齐。`gateway/channel_directory.py` 可作线索参考，不可直接充当批准名单或实时可达性证明。后端保存发送流水，但本期不开发该页的记录列表接口与弹窗。

### 2.9 原型边界与验收样例

专家管理页原型位于本仓库 `src/demo/components/ExpertChannelTab.vue`，候选样例在 `src/demo/channel-target-fixtures.js`。原型界面展示最终产品文案和状态，但当前候选、配置检查和测试发送仅更新浏览器本地状态，不连接真实消息平台；研发不得把这些结果视为实际权限或送达证据。

原型为每个专家的钉钉、飞书、企微提供隔离的人员与群聊候选；钉钉各五条，足以检查“四条可见、第五条滚动”。已加入名单的候选仍显示但不可再次批准。样例覆盖尚未验证、已受理、失败、未知和部分成功；升级本地数据不覆盖用户自建目标。消息渠道功能区不出现“历史模拟已受理”等原型状态文案，也没有发送记录按钮或弹窗。

验收时运行 `npm test`、`npm run build`，并在 `/experts/` 手动检查三平台切换、渠道接入、主动沟通、人员/群添加、候选搜索和完整 ID、批准与移除、检查配置弹窗、测试弹窗、文件开关及窄屏布局。正式后端接入后的真实发送验收按第一章执行。
