专家&项目 · 基于 Hermes 的实现方案

把「Worker（专家）+ Project（项目）」产品模型落到 Hermes 的 Profile / Kanban / Skills / Memory / Gateway 之上。

整理自架构分析与多轮设计讨论 · Hermes v0.16边缘扩展，不改核心

1. 产品理念

核心是建立「虚拟职场协作体系」，包含两类实体：拟人化的独立执行单元 Worker（专家/员工），以及团队化运作的容器 Project（项目）。结论先行：

大方向高度可行。 Hermes 本身就是按「具名专家协作」思路设计的——专家=Profile、项目=Kanban Board、技能=Skills/MCP、记忆=Memory、IM=Gateway，几乎正好对位。真正的工作量集中在产品 UI 层与少量元数据扩展，不需要改 Hermes 核心。

实体一 · Worker（专家）五大特性 ↔ Hermes

Worker 是拟人化的独立执行单元，每个员工有明确人设与职能边界。核心对应：一个「专家」= 一个 Hermes Profile。

特性Hermes 对应满足度说明
行业技能 Skillsskills/ + SOUL.md + toolsets + MCP完全每个 Profile 独立配技能、工具集、MCP
可进化 EvolutionMemory + Curator + skill patch部分是「记忆+技能迭代」，非模型权重学习
独立工作空间 WorkspaceProfile home/、workspace/ + Kanban workspace部分默认是状态隔离；真沙箱需 docker/modal 后端
记忆系统 Memorymemories/MEMORY.md + memory provider完全每个 Profile 独立、跨会话累积
状态持久化 Persistencestate.db（会话）+ task_runs（任务）完全会话与任务均落 SQLite，可中断续跑

实体二 · Project（项目）协作能力 ↔ Hermes

复杂业务不由单个员工包揽，而是把多位不同工种的专家拉入同一个「项目」团队化运作。核心对应：一个「项目」= 一个 Kanban Board。

能力Hermes 对应满足度说明
项目 = 虚拟团队工作空间Kanban Board完全一 Board = 独立队列 + 工作区 + 调度器，正好是「项目」粒度
多员工协作Task 的 assignee 指向不同 Profile完全Dispatcher 按 assignee 拉起对应专家执行
任务拆解kanban_create + task_links（父子依赖）完全编排者拆任务；依赖满足才 ready
信息共享 / 工序流转task_comments + run summary/metadata 向下游传递完全子任务自动读父任务最近一次完成的交接
项目成员名册assignee 软关联需自建Kanban 无正式成员表 → 产品层 project_members
共享工作空间Kanban workspace（dir:/worktree）需约定默认 scratch 完成即删，共享要显式指定共享目录
项目产物kanban_complete(artifacts) + task_attachments完全产物挂任务上，可随完成通知推送 IM
两实体落点： 专家=Profile（一人一套配置/记忆/会话/技能/IM）；项目=Board（一组 Task + 依赖 + 评论 + 看板）。一个 Task 只能一个 assignee（一个专家），多专家协作 = 多 Task + 依赖链，而非一卡多人。

4. 关键机制

Profile（= 一个专家）包含什么

身份与配置
  • config.yaml — 模型、工具集、终端、gateway
  • .env — 仅密钥 / Bot Token
  • SOUL.md — 人设 / 行为准则
  • profile.yaml — 角色描述（Kanban 路由用）
运行时状态（按 Profile 隔离）
  • state.db — 会话历史
  • memories/ — 长期记忆
  • skills/ — 技能
  • cron/ logs/ home/（子进程 git/ssh 隔离）

和某专家对话：hermes -p <name> chat / <name> chat / 该专家独立 Gateway。本质是把 HERMES_HOME 指到该 Profile。始终用 -p 指定专家，不要用 default（默认就是「主 Hermes」）。

Session vs Task：何时出现

状态SessionTaskassignee
和专家随便聊有无无
建了卡未派活可能有有创建时可指定
专家正在干活有有有

assignee 机制

  • assignee 是 tasks 表的单个字符串字段，值 = Profile 名。
  • 一 Task 一 assignee（无「多人负责一张卡」）。
  • Dispatcher 用 hermes -p <assignee> chat 拉起 Worker。
  • assignee 对应的 Profile 不存在 → skipped_nonspawnable，不会 spawn。
  • running 中不可改派；人工改派会清零失败计数。
是否要改 assignee 机制？——不需要。 多专家协作用「多 Task + task_links」表达；项目成员名册、卡片显示名等放产品层。只有当强需求是「一张卡多人共同负责且调度按多人语义」时才考虑动 schema，但那与 Hermes「一卡一人」哲学冲突，不建议。

6. 风险与边界（要管理预期）

点真实情况应对
「进化」是记忆积累 + 技能文档迭代，非模型学习产品话术定义为「记忆/技能进化」
「沙箱」Profile 是状态隔离，local 后端仍有用户级文件权限需真隔离用 docker/modal/ssh 后端
Worker 进程一任务一进程，非常驻 daemon；Dispatcher 才常驻「在线/忙碌」状态由 task_runs + active workers 推导
项目成员Kanban 无正式成员表，靠 assignee 软关联自建 project_members
一卡多人原生不支持拆子任务；或评论 @ 协作者/审核人
共享工作空间默认 scratch 完成即删项目任务统一指定 dir:<共享绝对路径> 或 worktree
细粒度权限只有命令审批 + 工具集粗粒度产品层 RBAC + 容器/工具集组合落地
对话 vs 任务两套独立存储（state.db / kanban.db）UI 聚合展示，底层不强行合并

7. 实施路线图（建议分期）

阶段一 · 打通底座（MVP）

  • 用 Profile 建几个专家；每个配 SOUL.md + 技能 + 工具集
  • 产品 UI：专家卡片墙 + 「和专家对话」（接 tui_gateway，始终 -p）
  • 对话页可「一键派活」→ kanban create --assignee 当前专家
  • 嵌入 / 复用 Kanban Dashboard 看进度

阶段二 · 项目协作

  • 一个项目 = 一个 Board；自建 project_members
  • 编排专家（启用 kanban toolset）拆任务、分派多成员
  • 项目详情页：看板 + 成员进度（按 assignee 聚合）+ 沟通日志（events + comments）
  • 共享工作空间：项目任务统一 dir: / worktree
  • 产物中心：artifacts + task_attachments 聚合展示

阶段三 · 体验与治理

  • 专家卡片元数据（头像/介绍/领域）+ 详情页全 Tab
  • 细粒度权限层（toolsets + 容器后端映射）
  • IM 渠道：每专家独立 Bot；完成/阻塞通知回推
  • 「进化」面板：记忆 + 技能使用/Curator 状态可视化
  • 对话任务与项目任务的统一「专家任务」聚合视图

8. 工程纪律（务必遵守）

不要改 Hermes 核心。 run_agent.py / cli.py / gateway/run.py 等是窄腰核心，改了会与 hermes update 冲突，也违背项目规约。
  • 能力在边缘：新能力优先走 CLI+Skill → service-gated 工具 → 插件 → MCP，最后才考虑核心工具。
  • 保护 prompt 缓存：不要在会话中途改系统提示/工具集。
  • Profile 安全：路径一律 get_hermes_home()，不硬编码 ~/.hermes。
  • 产品状态独立：成员表、元数据放自己的 sidecar DB，不混入 kanban.db / state.db。
  • 分存，不强合：对话(Session) 与 任务(Task) 分开存，UI 层聚合即可。

9. 待补充与开放问题

下列点在前面章节尚未充分覆盖，建议在进入开发前补齐设计或明确取舍。按优先级分三档。

P0 · 影响架构选型，需先定

缺口问题建议方向
多用户 / 多「老板」Hermes 偏单用户（一套 HERMES_HOME = 一个人）。产品若要多账号登录、各自看自己的专家与项目，Hermes 无内建账号体系。产品层做账号/租户体系：用户 ↔ 可见 Profile/Board 的授权表；后端按用户过滤。可结合 Hermes tenant 做软隔离，但硬隔离要靠产品层。
「资料」(输入) vs 「产物」(输出)需求区分了用户提供的资料与任务产物，但二者在 Hermes 都可能落在 task_attachments / workspace，语义未分。约定：输入资料 = 任务 attachments(uploaded_by=user) 或共享 dir: 下 /inputs；产物 = kanban_complete(artifacts) 或 /outputs。产品层加 kind=input|output 标记。
权限模型落地细粒度 RBAC（A.4 表）只给了「期望」，下发实现未定。明确翻译规则：allowed_toolsets→config.yaml toolsets；fs_scope→terminal.cwd + 容器挂载；approval_mode→approvals.mode。隔离强需求一律 docker/modal 后端。

P1 · 影响核心体验，二期前定

缺口说明 / 建议
自治循环 goal_modeKanban 支持 goal_mode（Ralph 式判官循环）让 Worker 反复迭代直到达标。适合「交付型」专家任务，需在产品「派活」表单暴露开关 + turn 预算。
定时 / 周期任务（cron）「数字员工每天巡检/日报」用 Hermes cron 实现（per-profile）。产品需有「定时任务」配置入口，映射 hermes cron add。
运维参数并发与稳定性参数未在产品暴露：max_spawn（全局并发）、max_in_progress_per_profile（单专家并发）、failure_limit（熔断）、model_override（按任务换模型）。建议项目/专家级可配。
tenant 多租户一个专家服务多个业务线时用 Kanban tenant 软隔离（workspace 路径 + memory key 前缀）。若产品有「一专家服务多客户」，对接 tenant。
端到端时序图建议补「对话→一键派活→Dispatcher→执行→产物/通知」与「编排者拆派多专家」两张时序图（可作附录 D）。

P2 · 细节 / 后续

缺口说明
「进化」可视化Curator 状态、技能使用计数、记忆增长的展示口径；明确「进化」= 记忆 + 技能迭代。
会话与任务的关联回填对话中派活后，把 worker_session_id 与 Task 关联，便于「这次干活对应哪段对话」。
安全 7 层落地用户授权、命令审批、容器隔离、MCP 凭证过滤、注入扫描、会话隔离、输入消毒——逐层确认在产品中如何暴露/默认值。
成本与用量per-profile / per-project 的 token 成本归集与展示（Hermes 有 usage 记录，可聚合）。
专家分发 / 模板用 hermes profile install <git> 把「预置专家」作为模板分发，加速新建专家。

附录 A · sidecar 数据模型完整 Schema

以下为产品自建的独立数据库（建议单独一个 product.db 或你们的业务库），绝不混入 kanban.db / state.db。所有与 Hermes 的关联都用「软外键」（字符串：board slug、profile 名、task id、session id），不做物理外键约束，避免与 Hermes 的生命周期耦合。

关联原则： profile = Hermes Profile 名（同时也是 Kanban 的 assignee 取值）；board_slug = Kanban Board；task_id / session_id 指向 Hermes 侧记录。产品侧只存「关系与展示元数据」，执行/会话/任务真相仍在 Hermes。

A.1 专家展示元数据

-- 专家卡片展示信息（Profile 名是主键，与 assignee 同源）
CREATE TABLE expert_meta (
  profile       TEXT PRIMARY KEY,   -- = Hermes Profile 名 / Kanban assignee
  display_name  TEXT NOT NULL,      -- 卡片展示名（可中文，≠ Profile 名）
  avatar_url    TEXT,               -- 头像
  intro         TEXT,               -- 一句话介绍
  domains       TEXT,               -- JSON 数组：擅长领域标签 ["财务","风控"]
  title         TEXT,               -- 职位/工种，如「高级开发」
  status        TEXT DEFAULT 'active', -- active | disabled
  sort_order    INTEGER DEFAULT 0,  -- 卡片墙排序
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

备选：也可写进各 Profile 的 profile.yaml（Hermes 已用它存 description）。若要让 Hermes 编排器也能读到「擅长领域」，写 profile.yaml 更合适；若纯产品展示，放本表更干净。

A.2 项目与成员关系

-- 项目（1 项目 = 1 Kanban Board）
CREATE TABLE project (
  board_slug    TEXT PRIMARY KEY,   -- = Kanban board slug（default / atm10-server ...）
  name          TEXT NOT NULL,      -- 项目展示名
  description   TEXT,
  owner_profile TEXT,               -- 项目负责人 Profile（可空）
  cover_url     TEXT,
  status        TEXT DEFAULT 'active', -- active | archived
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

-- 项目成员（Hermes 无此表——这是「把多位专家拉入项目」的核心）
CREATE TABLE project_members (
  board_slug    TEXT NOT NULL,      -- 关联 project.board_slug
  profile       TEXT NOT NULL,      -- 关联 expert_meta.profile
  role          TEXT DEFAULT 'member', -- owner | orchestrator | member | reviewer
  joined_at     INTEGER NOT NULL,
  PRIMARY KEY (board_slug, profile)
);
CREATE INDEX idx_members_profile ON project_members(profile); -- 「某专家参与了哪些项目」

role=orchestrator 的成员，对应在该 Profile 的 config.yaml 里启用 kanban toolset，使其能 kanban_create 拆派任务。

A.3 对话任务 ↔ 项目任务 聚合

-- 统一「专家任务」索引：把 Session 与 Kanban Task 合到一个列表展示
-- （只存指针 + 展示字段，内容真相在 state.db / kanban.db）
CREATE TABLE expert_task_index (
  id            TEXT PRIMARY KEY,   -- 产品内部 id
  profile       TEXT NOT NULL,      -- 归属专家
  kind          TEXT NOT NULL,      -- 'chat'（对话任务） | 'kanban'（项目任务）
  ref_id        TEXT NOT NULL,      -- kind=chat → session_id；kind=kanban → task_id
  board_slug    TEXT,               -- kanban 任务所属项目（chat 为空）
  title         TEXT,               -- 展示标题（对话可取首句/摘要）
  state_cache   TEXT,               -- 缓存状态（running/done/blocked…）用于列表快速渲染
  last_active_at INTEGER,
  created_at    INTEGER NOT NULL
);
CREATE INDEX idx_eti_profile ON expert_task_index(profile, last_active_at DESC);
CREATE INDEX idx_eti_board   ON expert_task_index(board_slug);
为什么要这张索引表： 对话(Session) 在 state.db、项目任务(Task) 在 kanban.db，是两套独立存储。UI 上要在「专家任务列表」里混合展示二者时，用这张轻量索引做聚合分页，避免每次跨库 JOIN。真相数据仍按需回查 Hermes。

A.4 细粒度权限（可选，阶段三）

-- 产品级 RBAC：最终落地为 per-profile toolsets + 容器后端 + 审批模式
CREATE TABLE expert_permission (
  profile       TEXT PRIMARY KEY,
  allowed_toolsets TEXT,            -- JSON：映射到 config.yaml 的 toolsets
  terminal_backend TEXT,            -- local | docker | ssh | modal（隔离级别）
  fs_scope      TEXT,               -- JSON：允许访问的目录（落地为 terminal.cwd + 容器挂载）
  approval_mode TEXT,               -- manual | smart | off（映射 approvals.mode）
  updated_at    INTEGER NOT NULL
);

本表是「期望权限」的产品表达，需由你们的下发逻辑翻译成对应 Profile 的 config.yaml 字段。Hermes 本身无 per-expert RBAC。
